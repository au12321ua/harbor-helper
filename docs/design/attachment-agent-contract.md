本次让成员及其授权研究 agent 选择明确版本的附件，独立完成发现输入、提交、跟踪和读取结果。附件更新产生新版本；通信重试找回同一次受理；执行结束、资源释放与报告可用分别可判断。

附件的核心意义是把任务与被评测 agent 的额外能力分开，让团队在同一任务和评分条件下比较无附件基线与提供附件后的表现，帮助判断能力是否改变。应用负责 API 及调用权限契约；帮助研究 agent 使用这些接口的 skill、CLI 与可能的客户端 SDK 独立提供，应用无需内置所有 agent 使用流程。

## 问题与已确认目标

当前 ZIP 上传已有内容摘要、安全路径检查和实验内冻结副本，但上传记录没有创建者、名称和可管理版本，也没有附件目录。现有 HTTP 与远程 CLI 共用受理、幂等和队列；身份访问主要依赖八小时登录会话，提交以通用字典校验，OpenAPI 入口关闭。状态查询已有执行及审计信息，但调用方需要推断报告是否可读。队列只有全局待处理容量，没有同一成员的受理分额；没有统一的暂停新受理及就绪契约。

已确认边界仍为受邀可信团队、成员/管理员两角色、共享结果与团队模型凭据。研究 agent 是代成员操作本服务的客户端，与容器内被评测 agent 分别识别。自动化授权不能进入附件、任务容器、模型环境或报告。网页成员完整操作与管理员日常配置继续保留。

以下权限细节、默认值和字段为本设计提案，不能倒称为用户既定要求。

## 附件如何复用与维护

附件是成员提交的 `skills/`、`sdk/`、`config/opencode.json`、`bootstrap.sh` 输入，沿用当前格式及校验；不是任务作者的 Docker 环境，也不引入新的环境包格式。

附件可选，无附件是有效基线，提交和页面必须允许明确清除附件选择，不自动沿用上次选择或默认附加某版本。对照实验固定任务/数据及评分来源、基础 agent/模型、作者参数、尝试次数和资源/时长等既有条件，主动新建使用候选附件的实验；不能用普通 rerun 隐式改变附件。详情和比较同时展示“无附件”或具体版本/摘要，附件变化是预期实验因素。

比较中的版本身份仅取各实验冻结的 `attachment_version_id`，不按摘要反查当前版本库。无冻结引用且内容摘要为空时才显示“无附件”；有内容摘要却无可知谱系的旧实验显示 legacy 与原摘要。旧上传后来登记成版本，也不追认旧实验当时使用了该版本。

现行 `results/reports.py:compare` 已允许 `bundle_digest` 不同，并通过 `bundle_change` 返回附件差异；本次沿用该语义和其他条件门槛，补必要版本身份展示与基线/候选专项验证，不新增通用“允许变化因素”系统。任务/模型等其他条件变化、缺评分或失败仍给出原因；分数变化是该固定实验的观察，不自动宣称通用能力提高、统计显著或附件完全无副作用。任务作者输入、评分器与参考解属于任务侧，不能把候选附件制作成修改评测答案的机制。

每个附件有稳定身份、显示名称、创建者和创建时间；每次成功发布产生不可变版本，记录版本序号、发布者、发布时间、内容摘要、可选说明及派生来源。显示名称允许重名，调用按身份与版本选择；“最新版”只帮助发现，提交必须给出明确版本。即使两个版本内容相同，它们的发布记录仍独立；内容复用不混淆作者与权限。

所有成员可列出、查看元数据和复用团队附件，创建自己的附件，或上传内容创建派生附件并记录来源版本。创建者及管理员可改名称/说明、发布后续版本和停用/恢复；其他成员通过派生维护自己的分支，不覆盖他人的历史。成员停用后，其现有附件仍可由团队使用和管理员维护，不因身份停用隐式删除输入。本次无需引入原始附件下载端点，派生时仍上传自己的内容；不能宣称已具备在线编辑或自动差分。

停用附件或某版本阻止其新的提交、重跑及准备失败后的新恢复受理；已受理任务继续使用冻结输入。历史记录可查看，不能替换或删除已引用字节。本次用停用处理日常维护，物理删除和附件库空间回收留待有引用检查的后续设计；现有日志/产物保留机制不得顺带删除版本库。

普通情况：成员发布 v1，另一成员或研究 agent 用 v1 提交；后来发布 v2，仅主动选择 v2 的新实验使用它。超时后的版本发布重试使用同一幂等键，返回原版本，不重复递增。并发发布保证各自得到唯一序号；相同键而内容/目标/说明不同返回冲突。ZIP 解包失败或进程中断不会产生可选的半成品版本。

新建附件并发布 v1、发布后续版本、派生和登记旧上传均是幂等写操作，并均提供按键找回结果的方法。其操作类别固定，不把目标附件 ID 或来源 ID 编入操作类别：相同成员在同一类别复用键而改目标也必须冲突。规范请求摘要包含下表字段与校验后的解包内容摘要，不依赖 ZIP 压缩字节、客户端声称的 digest 或字段顺序。校验失败不落键；只有已提交的身份/版本才登记键。并发和崩溃恢复须保证身份、版本与键同一次原子可见，重试不能留下多个空身份。

| 固定操作类别 | 请求摘要包含的语义字段 | 同键找回对象 |
| --- | --- | --- |
| `attachment_create` | 名称、说明、实际内容摘要 | 新附件及 v1 |
| `attachment_publish` | 目标附件 ID、版本说明、实际内容摘要 | 原发布版本 |
| `attachment_derive` | 来源版本 ID、新名称、说明、上传内容摘要 | 派生附件及 v1 |
| `attachment_register` | 旧 bundle ID、新名称、说明、重新校验的内容摘要 | 登记附件及版本 |

读取原幂等结果仍要求当前身份及相关操作能力；找回既成发布不重新执行停用检查或生成版本。对已删除或损坏的输入只返回明确不可用状态，不伪造恢复内容。

旧上传不猜作者：保留 `bundle_id` 与字节，显式显示“历史上传，创建者未知”。旧 ID 仍能按原契约用于新提交，历史实验不改写；用户可将它登记为新附件的一个版本，记录登记者而非伪造原上传者。登记后旧 ID 对应同一版本，并受停用检查，避免绕过新管理规则。同一旧 ID 不重复登记到多个可独立停用的身份。准备阶段再次验证摘要，内容失配作为输入故障停止，不能悄悄改用最新版。

新受理把明确的 `attachment_version_id` 和底层 `bundle_id` 一同写入冻结绑定，旧 ID 提交也记录其底层 ID；沿 rerun/retry/recover 继承附件谱系，在当前受理时检查对应停用状态。不能仅依赖 rerun 的空请求体。存量父实验若有旧 ID，在登记后停用会阻止其新的历史重跑；若完全没有谱系字段，按旧契约复制父实验快照，标明 legacy/unknown，不按摘要猜身份或重写旧 manifest。冻结副本来源和摘要仍照常验证。

## 一次授权后的 agent 实验闭环

成员在网页创建有名称与到期时间的自动化访问凭证，签发时复核当前密码，不能单凭已取得的八小时会话铸造长期凭证；原值只在签发响应显示一次，持久层仅存摘要。网页列出所属成员、用途、到期与撤销状态；成员撤销自己的凭证，管理员可撤销任何凭证。默认建议有效期 30 天，签发时可选具体到期时间；这是可调整产品默认值，不是预算或用户硬限制。账户停用、凭证到期/撤销立即阻止后续 API 调用，密码重置也撤销该账户自动化凭证。

凭证只能授予其成员已有操作的子集：发现/读取共享数据，上传及维护自己有权维护的附件，提交/重跑，以及取消自己的任务。签发时可选这些固定能力；默认只读，允许执行须显式选择。自动化凭证本次不提供管理员配置能力，即使签发者是管理员也不授予取消他人任务、读取密钥或变更团队设置。浏览器登录会话保留原角色能力。凭证不能签发其他凭证，不能扩大权限；多凭证仍属于同一个成员，不能绕过额度。请求记录同时保留成员身份与非秘密凭证 ID；重跑归当前调用成员。

重跑/修复/恢复只继承研究输入绑定；成员 ID、提交者、受理 ID 和自动化凭证 ID 重新取当前调用身份，不能继承父凭证。浏览器受理的自动化凭证 ID 为空；模型 credential ID/version 与访问凭证 ID 是不同字段，不能混用。

访问凭证采用可识别格式：`hh_pat_v1_` 前缀加 32 字节随机值的 43 字符 base64url 表示。所有附件上传、版本发布、派生、登记，以及将历史附件用于新受理/复制到新任务前，按文件字节扫描完整树，拒绝这种完整凭证格式。请求阶段还拒绝当前请求实际出示的明文访问值（包括旧会话 bearer）；重跑在受理时检查父快照。当前原值仅在请求内存用于验证/扫描/脱敏，不写文件、日志、数据库或子进程环境，后台准备/复制仅作格式扫描，不能为扫描把访问值传入 worker。格式拒绝适用于其他成员、已撤销及已过期的同格式凭证；识别到只报安全错误，不回显命中值或文件内容。错误/结果/日志脱敏也覆盖该格式，fixture须覆盖普通文件、二进制文件和历史路径。此检查针对可识别明文，不声称能发现任意编码、加密或分片秘密；可信团队仍须避免把访问凭据打包。

通过 HTTP 发布版本化输入/结果 schema 与简短调用说明，远程 CLI 使用同一业务操作。发现返回可用数据集及其验证状态、任务选择方式、模型方案、附件版本、当前资源限制和本凭证允许的操作，不输出模型/Hub key、密文、宿主路径或原始诊断。任务目录复用现有按范围读取能力，不为发现全量下载所有任务。声明能力不保证外部依赖下一刻仍可用；受理仍检查当前绑定、版本和限额。

应用以公开 API 契约为中心交付资源/操作、类型化输入输出、版本、认证及每个操作的能力要求、幂等和状态/错误/续读语义；权限在服务端统一判定。Web、CLI、SDK与MCP都调用同一接口，不拥有独立授权规则或队列。能力发现应说明缺失权限与允许操作，不能靠客户端界面隐藏功能代替拒绝未授权调用。

客户端使用层另提供一个最小研究操作 skill，教 agent 配置访问凭证、发现输入、以原键找回受理、等待安全报告，以及开展无附件/附件对照；可复用现有远程 CLI，或直接使用 HTTP。客户端 SDK 根据实际需要封装请求、类型和恢复方法，不把服务特定研究编排写进应用，也不把每个 agent 框架适配变成服务发布前置。客户端 skill/SDK 是调用本服务的工具；实验附件内 `skills/` 和 `sdk/` 是给被评测 agent 的额外能力，两者的凭证和生命周期不能混用。

标准流程：发现 → 选择任务、模型方案、明确附件版本 → 保存请求正文和稳定幂等键 → 提交取得受理 ID → 查询受理并取得 run ID → 按服务建议间隔轮询 → 在报告可用时读取结构化结果。提交结果同时提供找回原受理的方法，避免必须先知道响应里丢失的 ID 才能恢复。

通信超时：以原正文和原键再次提交，或按成员、操作与键查询受理。不同凭证或网页会话，只要同一成员，就能找回同一次受理；其他成员不能借键访问请求正文。键不存在只说明尚未观察到受理，重发仍必须用原键。已有受理匹配在暂停/额度检查之前返回，避免维护或额度变化让通信重试失败；身份与能力验证仍在最前。已落库键不随短期凭证到期或原始证据清理而失效。

主动重跑、修复重试或失败准备的新恢复是新操作，需要新键和显式调用，保留父关系，不与通信重试混淆；沿用现有重跑/修复差别。修复重试不能偷偷切换附件。想评估 v2 应明确新建实验，不能把旧实验重跑解释成改用最新版。客户端不因 429/503 自动换键重试，也不自动批量生成带费用的实验。

MCP 本次作为同契约的可选薄入口，实际研究客户端尚未明确；API+权限契约及一个实际可用的独立 skill/非交互客户端流程验收闭环，不能把 MCP 当自动化能力的替代。确定客户端需要时再接 MCP，不另建身份、队列和状态逻辑；完整 SDK 与更多客户端适配按实际需求独立迭代。

## 状态、错误与容量的可观察行为

新增结构化视图，兼容保留当前状态字段。受理阶段为准备中、已产生实验、准备失败或已取消；实验保留排队、启动、运行、清理阻塞和原终态。执行资源是否释放、证据审计是否安全、报告是否可用独立表示，不能合成一个成功布尔值。

以下枚举用于公共视图，不要求迁移旧执行状态；各状态附明确 reason，缺证据不能伪装成已确认。

| 轴 | 枚举与派生规则 |
| --- | --- |
| `resource` | `active`：starting/running/cancelling；`cleanup_blocked`：执行资源未确认释放；`released`：尚未分配资源的准备/排队，或按原生命周期已确认释放的终态；`unknown`：缺少可依赖的执行/清理证据 |
| `audit` | 沿用 `pending/clean/incomplete`；尚未形成实验/审计记录返回 pending 并注明 not_started，历史缺信息如实说明 |
| `report` | `blocked`：审计 incomplete，或待审计而进度不可确认；`available`：实际存在可读安全报告（含过期后的安全摘要）；`pending`：确有进行中的执行/报告生成/审计路径；`unavailable`：已终态且缺报告、准备失败或已取消且没有实验，附 missing_report/preparation_failed/cancelled_before_run 等原因 |

报告判定首先守住原资源/审计门槛：存在文件不等于可读；未终态或资源释放未确认不能提前发布。audit clean 且资源门槛满足时，存在安全报告才 available，否则终态为 unavailable。审计 pending 而 scheduler 活动无法确认时，报告 blocked（reason=audit_progress_unknown），不伪造永久前进的 pending。状态读取/证据来源失败以安全错误或 unknown/blocked 表示，不能返回空报告作为成功。scheduler另有 `ready/unavailable/unknown` 就绪状态，不凭文件存在或陈旧观察宣称 ready。

执行容量继续由原执行状态与实际资源确认决定，绝不按 audit/report 占用；`unknown` 显示本身不新增容量阻塞，无释放确认的既有执行资源仍按原清理规则保留。有效 0、缺评分、执行失败在安全报告内仍分别表示，不能从上述枚举推断 reward。

| 观察 | 调用方下一步 |
| --- | --- |
| 准备/排队/执行中 | 查询原受理或实验；显示当前等待原因与建议轮询间隔 |
| 清理阻塞 | 资源容量仍占用；联系管理员，不能视为完成后立即重复提交 |
| 执行已结束，审计仍待完成 | 资源按实际确认释放；等待报告，继续查询 |
| 审计异常 | 报告/相关原证据为 blocked；联系管理员，不能读取未经审计内容 |
| 有安全报告 | available；失败实验也可能有可读报告；有效 0、缺评分、执行失败分别保留 |
| 已终态且无法生成报告 | unavailable 与明确原因；不能永远 pending 或返回空对象当成功 |
| 原证据已过期但安全摘要仍存在 | 安全报告可读，原文件过期另列，保持旧保留语义 |

排队原因先提供可验证的当前原因：全局 job/trial 容量、请求大于当前容量、执行资源清理阻塞、调度器不可用；不承诺预计开始时间或调度公平性。没有已验证原因时返回 unknown，不猜测。

错误保留现有 `code/message/request_id/retryable`，增加稳定动作类别：`retry_same_request`、`poll_existing`、`fix_input`、`reauthorize`、`contact_admin`、`explicit_new_attempt`。只基于现有已知错误映射，未知错误给安全的人工诊断动作，不扩大成全面故障归因。动作可携带相关受理/实验 ID 和建议等待时间；建议时间不是完成保证。429/503 提供 `Retry-After` 或明确的未知等待，幂等冲突不得建议自动生成新键。

在现有全局 `max_queue` 外增加管理员网页可调的每成员待处理额度。准备中与已排队合计，每个受理仅计一次；运行任务继续由原 job/trial 限制控制，清理阻塞按资源规则保留执行容量。所有入口及同一成员的所有凭证共用额度，管理员提交也计入自己的额度。超限拒绝在创建新受理前返回身份额度原因；已有幂等受理不占新额度。降低额度不取消存量，只限制后续新受理。

计数须覆盖准备发布的崩溃窗口：preparing仅计 `target_id` 尚未进入 runs 的受理；一旦对应 run 已落库，按 run 当前 queued/active/terminal状态计数，即使 submission 尚未改 ready。成员计数按可靠的 `user_id` 归属；无 user_id 的历史/local run不猜成员，也不计成员分额，但仍沿全局队列/执行容量规则处理。有效成员上限始终取 `min(配置成员额度, max_queue)`。检查与新受理写入在同一control段完成，不能先计后并发插入。

默认提案为每成员最多 `min(10, max_queue)` 个待处理受理，管理员可按实际团队负载调整；不把该数字写成验收唯一值。它缓解单身份占满默认全局队列，不能保证任意团队规模都不排队，也不改变目前调度算法或宣称防止大任务饥饿。未来按实际负载再决定公平调度或 MQ。

## 维护与兼容风险

管理员网页可暂停/恢复新受理，并显示维护原因、可选重试时间和当前受理状态。暂停持久保存，重启不能自动开放；暂停覆盖 submit/rerun/retry/recover 的新受理。已受理准备和队列继续排空，查询、取消及取安全报告可用；暂停不是终止 scheduler，更不等于可以立即备份。

维护开关写入与受理检查使用同一 control 锁：受理在锁内读取当前持久值，不使用请求开始时或进程里的旧缓存。暂停写入成功后，后取得锁的调用只能找回旧幂等受理或被拒绝创建新受理；暂停前已经落库的继续排空。恢复也遵守此顺序，不借重启刷新隐式开放。

提供就绪视图，分别表示初始化、是否允许新受理、调度器是否实际可用及状态观察时间。调度器根据当前进程身份和更新的活动观察判断，不能仅信旧 `scheduler.json` 文件存在；观察过旧返回 unknown/unready。具体心跳阈值由工程根据调度周期确定并在接口说明。未就绪拒绝新的实验受理，旧幂等查询仍可用。匿名只给最小存活/就绪布尔值，维护详情仅已授权成员查看，不输出内部路径/PID/配置。查询接口不能证明 Docker/Hub/模型全过程成功。

附加 schema 与数据按迁移创建；不重新 init，不更换主密钥，不改写旧冻结 manifest、评分和证据。迁移失败保持旧数据、明确拒绝以新版本服务继续写入；升级前仍须核对所有写者并保全一致备份及外 master。只回退代码不能恢复新 schema，正式发布须交付兼容说明和基于最新业务数据的恢复步骤，不能覆盖新业务。

附件有可执行内容，格式校验不能证明脚本可信或发现所有硬编码秘密；沿用可信团队边界，保留现有路径/凭据文件检查，不声称增加了完整内容安全扫描。访问凭证是新的敏感输入，HTTP异常、代理访问日志与客户端示例须避免输出 Authorization/原值。模型费用仍为 unknown 时如实返回，时长与并发限制不是金额保证。本轮设计和普通验证没有真实模型请求授权。

## 验收故事

1. 两名成员分别通过浏览器与一次授权的 HTTP 客户端发现任务和附件 v1，提交并取得安全报告；发布 v2 后能主动用于新实验，v1 的历史字节/摘要/引用不变。其他成员不能覆盖原附件，可派生；停用阻止新受理，已受理不变。
   同期用脚本化客户端及 fixture/Oracle 验证同一固定条件的无附件基线、附件 v1 候选及 v2 新候选契约：无附件可明确选择/清除，比较显示 bundle_change 与冻结版本且不因附件因素拒绝；其他条件变化仍说明不可比原因。真实模型的表现差异与真实 LLM 研究 agent 不作为发布前置，也不隐含至少三次付费实验；它们在另获授权/预算后的研究中验证，观察不能冒充统计或通用能力结论。
2. 版本发布及实验提交在响应丢失、并发请求、服务重启后，以同键找回原对象；不同输入冲突。成员跨凭证找回，同键跨成员不混用；旧 bundle ID 登记、停用及历史重跑的兼容行为分别验证。
3. 签发须复核密码，凭证只显示一次；到期/撤销/密码重置/账户停用均阻止后续调用，scope不足和取消他人任务明确拒绝；可识别明文凭证进入任意附件文件时拒绝发布/登记/复制，worker环境及安全输出无该值。另验重跑使用当前成员/凭证而非父凭证，明文扫描与通用内容安全的范围分别记录。
4. 同成员多凭证及网页共同达到可调额度时，只拒绝新的受理，不重复计准备/队列、不影响已幂等受理；另一成员在全局容量可用时可受理。降低额度、准备失败、取消及并发时计数正确。
5. 维护在并发受理和重启后保持；已受理能排空，cancel/read可用，既有幂等请求可找回。scheduler 不可用如实拒绝新受理，不能把“维护暂停”误报为正在安全备份。
6. 按三轴枚举验证有效零分、缺评分、执行失败、终态无报告、审计异常、资源清理阻塞与原证据过期；scheduler不可用/unknown不伪造报告进度，unknown资源不凭显示新增容量阻塞；原安全证据门槛和释放容量语义不降低。
7. API契约明确每操作权限，未经授权调用在服务端拒绝；用独立skill中的操作路径与脚本化薄CLI/HTTP客户端验证发现→对照提交→恢复查询→结果获取，服务无需新增agent框架专用业务路径。发布验证不要求真实LLM研究agent或付费模型；真实使用证据有授权/预算时另列，不能将脚本/fixture/Oracle说成LLM自主能力或效果证明。

Fixture 与隔离 HTTP/浏览器测试验证权限、事务、故障和兼容；代表性真实 Docker/Harbor 小集验证附件确实进入任务并可产出报告。任务选型按公开可获取依赖、适中资源、可靠评分和工具流程覆盖，具体固定任务及资源前置在执行前登记。取消/重启/清理故障用专项检查，不假装普通 benchmark 覆盖。真实模型闭环须另核当前凭据授权和预算；Oracle、假模型或 fixture 不证明真实模型效果。Harbor升级只围绕配置转换、原生生命周期和结果解析补兼容证据，不趁机引入通用执行器/沙箱框架。

## 实现草图（供工程判断，不增加需求）

可能在 `service/data.py` 为附件/版本、自动化凭证与维护状态增加独立记录；版本仍指向已有 bundle 存储，发布用暂存、摘要验证与唯一键完成原子可见性。幂等范围复用成员+操作+键，版本发布和登记也采用该规则。崩溃遗留的暂存字节可精确收尾，但不可清除已引用对象。

`service/application.py` 负责版本权限、冻结引用、跨入口受理及额度；`service/api.py` 增加类型化 schema、凭证能力校验与错误动作。保留 `/bundles`、`bundle_id` 和原响应字段；新提交可选明确的 `attachment_version_id`，两种引用同时给出应拒绝，不能隐式猜优先级。历史兼容与新停用检查共享映射。

预期的新增接口可为附件目录/版本发布、自身凭证签发列表撤销、按键查受理、schema、授权状态/就绪及管理员维护开关；具体路径与字段在实现时形成一份契约，不在此重复造另一套 API。分页/范围参数与 schema 明确上限和续读方式，避免 agent 必须全量读取记录找回受理。

执行层只增必要的凭证 ID/附件版本非秘密追溯字段与状态观察，不改变作者环境/工具注入和原报告权限；`commands/remote.py` 与前端共用这些操作。新增页面为附件选择/版本维护、自身自动化凭证和管理员维护/成员额度，本次无需整体视觉重做。

## M4 实施记录

**2026-10-23，数据集与准备。** 与 M6 并行开发，按用户指示合并时以 M6 的结果为底、重新生成迁移 `0001`。以下是实现中的选择，均为设计建议层面，未经用户逐条确认；与原设计不同的已写明原写法和理由。

| 事项 | 原设计 | 实际做法 | 理由 |
| --- | --- | --- | --- |
| Hub 接入 | 02 第 4 节：search / list_versions / describe_version / fetch_content | 每次目录调用启动一个 Runner 进程执行一条 `hub` 命令，返回一条结果事件；服务进程仍不加载 Harbor。团队 Hub 凭据只通过这个子进程的 `HARBOR_API_KEY` 传入，HOME 每次新建，不使用本机登录。Harbor 0.24.0 没有数据集搜索接口（`list_datasets` 未实现），搜索直接按名称查询 Hub 的包表 | 与执行共用版本锁定的 Harbor；凭据不落盘、不进日志 |
| 内容身份 | 02 第 3 节：上游 digest 与本地材料摘要分开 | 下载后用 Harbor 自己的打包哈希核对上游 digest，不符即“内容不符”；另算一份本地文件摘要（材料摘要）。任务材料按上游 digest 存放，每次使用前按材料摘要校验，校验不过就重新下载 | 两个摘要各管各的，不互相替代 |
| 导入 | 02 第 3 节 | 管理员网页发起导入 Operation：解析引用 → 逐个下载并核对 → 检查清单 → 一个事务登记版本、任务和 pending 准入。下载遇到鉴权、暂态、不存在或不符时整个导入失败、不留半个版本；清单不受支持的任务照样登记，在首次准备时以 `PREPARATION_UNSUPPORTED` 失败。数据集级文件或指标暂不支持，导入被拒 | 版本要么完整、要么没有；不支持的原因留在任务上便于管理员查看 |
| 重复导入与标签漂移 | 02 第 3 节第 6 条 | 同一内容返回已有版本；同一引用指向新内容时返回 `CONTENT_REFERENCE_CHANGED`，管理员勾选确认后作为新版本登记。重复导入还会重新核对此前标为“内容不可得”的任务内容，取得同一 digest 即恢复为可得 | Hub 无法区分“已删除”和“当前凭据看不到”（见 Harbor 上游问题清单），需要一条让管理员恢复的路 |
| 作者参数 | 02 第 3 节、03 | 从 task.toml 的环境变量模板和作者 compose 文件的变量中发现，保存默认值、是否必填、是否敏感和出现位置；资源一律标 `constraint_strength=unknown`。必填且无默认值、或敏感且无默认值的参数在 M5 能填写取值之前，作为 `CONFIG_REQUIRED_MISSING` 阻止提交 | 不让运行带着缺失的输入启动；取值属于 M5 的配置解析 |
| 不支持的任务 | — | GPU、独立验证环境、分步环境、没有环境定义的任务在首次准备时失败，不准入 | 平台准备只覆盖主环境（O-09 不做 GPU） |
| 准备规格 | 02 第 6 节的字段 | 照列，但不含 `dataset_resolved_digest`；加入环境定义目录摘要和构建时限 | 不同版本里内容相同的任务共用一份缓存 |
| 平台自己准备 | 02 第 5 节、M1 TECH-03 | 有 Dockerfile 的任务用可复现设置（不写 provenance、固定时间戳）`buildx build`，作者给出镜像的任务按仓库 digest 固定后拉取；结果按镜像 ID 识别，标记为 `maestro-prep/<实例>:<规格>`。交给 Harbor 的是任务副本，`docker_image` 指向这个镜像并设 `pull_policy: never`，Harbor 不再构建或拉取。镜像只带规格标签，不带实例标签 | 实例标签会让同一内容在不同实例得到不同镜像 ID，并会被按实例标签的清扫误删 |
| 准备原件（U-17） | 02 第 5 节 | 成功后 `docker save` 到 `data_dir/preparations/<规格>.tar` 并记摘要。恢复依次：本机镜像在且 ID 相同 → 直接用；原件摘要相符 → 载入；都不行才按固定来源重建或重新拉取，镜像 ID 不同即“内容不符”，不发布，环境镜像记为不可得 | 原件是数据而不是缓存，放在数据目录、计入磁盘水位 |
| 准入与可得性 | 02 第 5 节 | 准入按任务与准备方式记录，首次成功的证据含 Operation、规格、两个摘要、镜像 ID 与原件摘要；失败记 `first_failed` 与原因，只有管理员可重试或撤销。内容可得性按（摘要，资源种类）记录，资源种类有任务内容和环境镜像两种；只有“确实不存在或内容不符、且本机没有已校验的副本”才记不可得，暂态和鉴权失败从不改它 | 同 02；一个任务的两种必要内容分开判断 |
| 共享恢复 | 02 第 7 节，D-020 | 每个缓存键同一时刻一个恢复 Operation（带租约和代次）。等待者是运行（D-020，`preparation_waiters.attempt_id` 改为可空），或管理员的首次准备 Operation（新增 `holder_operation_id`）。最后一个等待者离开时结束恢复；正在结束的代次不再接受加入。发布时核对代次、Operation 和租约，并在同一事务把使用 pin 交给每个等待者；被取代的恢复记 `STALE_PREPARATION_LEASE`，其等待者重新加入新的代次 | U-06 要求保留共享恢复与租约 |
| 运行的准备阶段 | D-020 | Runner 启动前为每个任务取得 pin，缓存冷时加入共享恢复；等待期间试次保持排队、阶段显示 `restoring_cache`。运行领取时已整体预留容量，等待恢复期间仍占用 | 运行级调度的折中。02 要求不为等待预占模型提供商槽位，Oracle 运行没有提供商，M5 接入模型时需重新安排 |
| 恢复失败的计数 | 02 第 7 节第 6 条、06 第 4 节 | 每次失败的恢复对每个等待试次记一次执行尝试，原因码 `PREPARATION_RESTORE_FAILED`、`RESOURCE_CONTENT_UNAVAILABLE` 等，错误中带期望摘要、Operation 与建议动作。只有暂态失败按 D-011 退避重试（最多 3 次尝试），鉴权失败和内容不可得不重试；执行器的尝试编号接在这些之后 | F-05：尝试增加、试次数不变、准入不变，恢复本身不做内层重试 |
| 并发与资源 | 02 第 7 节第 3 条 | 同一进程最多同时 2 个恢复；构建占用的 CPU / 内存不计入主机执行容量 | BuildKit 无法按构建限制资源（M1） |
| 回收 | 02 第 8 节：按配额和 LRU | 只实现管理员手动回收（Operation）：先认领再删除本机镜像，原件和准入保留；有 pin 或正在恢复时拒绝 | 自动回收的配额与触发时机还没有依据 |
| 重启 | 02 第 8 节 | 上一进程的导入、首次准备、恢复与回收 Operation 标为中断；恢复中的缓存退回 stale / absent 并记原因；等待者与 pin 全部作废；清掉临时镜像标记。docker 客户端随服务退出（父进程退出信号），BuildKit 随之取消构建 | 不替旧进程编造结果；准入与证据不动 |
| 删除与回收站（M6 交接） | U-19 | 导入遇到在回收站里的数据集或同一内容的版本时拒绝，提示先恢复；已物理删除的只剩回执，可以重新添加（数据集与版本的唯一约束改为普通索引，由导入的写事务检查）。物理删除版本时一并删除不再被其他版本使用的准备记录、镜像和原件，删除前再查一次是否已有新的准备记录；材料与物理删除并发时，使用前的校验会发现缺失并重新下载 | 补上 M6 记录中留给 M4 的待办 |
| 评分契约确认 | 06 第 2 节，M6 记录 | 管理员在版本页确认指标名称、方向和通过阈值，写入版本清单的 `scoring_contract`；之后受理的运行冻结它，已受理的不变 | M6 已从清单读取契约，确认入口属于导入流程 |
| 开发命令与演示 | M3：`dev-local-dataset` 直接登记为已准入 | 改为在服务停止时，用真实 Docker 环境走一遍导入和首次准备；`serve --demo-executor` 不再预置数据集，改由管理员从假数据源添加 | 开发路径与正式路径一致 |
| Runner 协议 | — | 修正 `emit` 的参数名与事件字段 `kind` 冲突（改为仅位置参数） | 接入 Hub 错误分类时发现 |

验证范围：服务测试 152 项通过，其中 M4 新增 E2E-DS-01～05 的假数据源 / 假环境版本（全部经 HTTP）：导入固定内容、重复导入不重复登记、标签漂移需确认（F-11）；三任务中一个首次失败、按全部可提交提交 2 个、管理员重试后 3 个、旧快照不变、回收两个缓存后仍可选并在运行内恢复（F-21）；只读与 experiment PAT 可读但两类 PAT（含管理员的）都不能导入、准备或回收，read PAT 不能提交；网页成员与 PAT 两个运行同时等待一次恢复、取消一个不影响另一个、按原配置再提交不再恢复且只扣一次额度（F-22）；最后一个等待者离开即结束恢复；暂态失败两次后成功（F-05）、鉴权失败不误判不可得并给出凭据入口、确切内容消失后阻止提交且带期望摘要且不扣额度、重新导入后恢复、重建得到不同镜像不发布、上游丢失但本机副本仍在可以执行（F-23）；被取代的恢复不能发布、杀进程留下的恢复在重启时对账（F-24）；作者参数、不支持的任务与撤销；物理删除版本回收缓存但保留共享内容、导入尊重回收站、评分契约确认。真实 Docker 测试 5 项通过：首次准备为可复现构建并导出原件，Harbor 使用准备好的镜像而不构建或拉取（运行前后镜像列表相同），回收后载入原件恢复为同一镜像 ID，删除原件后可复现构建重建为同一镜像 ID 并重新导出；M3 的 4 项照常通过（开发命令已走真实准备）。真实 Hub 测试 2 项通过（匿名、公开的 `harbor/hello-world`）：搜索、版本、按标签与按 digest 解析、不存在的修订记为不存在、无效 key 记为鉴权失败；经 API 导入并完成首次准备（真实构建），重复导入返回已有版本。网页在全新演示实例上用 Playwright 走过：从数据源添加、首次准备后三类状态、回收缓存后显示“运行时恢复”、任务详情；M3 留下的模拟数据测试补齐字段后也通过。前后核对本机镜像列表不变，无残留容器和网络。环境：服务 CPython 3.13，Runner CPython 3.13 + Harbor 0.24.0，Docker 29.9.1（buildx 0.38），Linux 6.8。

未覆盖：自动回收（配额、LRU）与磁盘紧张时的回收顺序；构建资源计入主机容量；用真实团队凭据读取私有数据集（没有授权的 key，只验证了无效 key 的分类）；作者给出预构建镜像的任务的真实拉取路径（只有假环境）；真实 Hub 任务的 Oracle 执行（hello-world 的验证器要在容器内联网，属于 M5 的网络策略）；compose 任务的变量发现只有单元路径；作者参数的取值、`config-resolutions` 与重跑接口（M5，DS-04 的“原配置重跑”以相同配置再次提交代替）；准备方式变更后的重新准入入口；恢复等待只受运行总时限约束，没有单独的等待时限；多位置缓存。

## 独立审查与修复记录

**2026-10-23，对 M2、M3、M4、M6 的独立审查及修复。** 起因：用户只看过汇报、没有读过代码，要求独立评估。审查在 `302b2ff` 上进行，用清空环境重跑测试，并在全新实例上走了真实进程；四个审查者分别查数据集与准备、结果与回收站、身份与 API、执行内核，每条发现都另行重跑复现脚本确认后才修。修复在 `fix/review-findings` 分支上完成，每条带先失败后通过的回归测试。原始复现脚本与报告在 `/tmp` 下，不入库。用户决定见 U-20；以下是实现中的选择，均为设计建议层面。

| 事项 | 原做法 | 新做法 | 理由 |
| --- | --- | --- | --- |
| 实时日志读取 | Runner 的 `tail()` 用 `is_file()` / `open()` 读容器可写的 `agent/`、`verifier/` 目录 | 不跟随符号链接：`O_NOFOLLOW` 打开并核对真实路径仍在试次目录内；归档不再 `copytree`，只复制普通文件，数量（500）、单文件（64 MiB）和新增的每次尝试总量（1 GiB）在复制过程中生效；跳过的文件仍在清单里并带原因（`SYMLINK`、`TOO_LARGE`、`TOO_MANY_FILES`、`TOTAL_LIMIT`、`UNREADABLE`、`COPY_FAILED`），清单最多列 200 条、其余只计数（协议新增可选字段 `skipped_unlisted`） | 容器能写这些目录（C-07），符号链接可让宿主机文件进入全团队可见的日志 |
| 凭据加密 | 停用或启用只改 `revision`，而密文的附加数据绑定 `revision` | 停用或启用时在同一事务里按新 `revision` 重新加密；因此改状态需要主密钥可读 | 否则停用后启用的凭据无法解密，任一停用的凭据还会让主密钥轮换失败 |
| Hub 检索 | 任何登录主体都可检索外部数据源并使用团队 Hub 凭据 | 只有管理员网页会话（U-20）；同时限制同时运行的 Hub Runner 进程为 4 个；导入拒绝已删除的凭据 | 用户决定 |
| 登录限流 | 按用户名计数，成功登录也计入，键永不清理，用户名无长度限制 | 只计失败；每个账户的桶按（用户名，来源地址）区分，来源地址另有桶，上限为账户上限的 5 倍；空键淘汰、最多保留 4096 个键；用户名最长 128、密码与令牌最长 256；`/me/password` 连续输错当前密码 10 次后锁定。`login_attempts_per_minute` 的含义改为“每个账户每个地址每分钟失败次数” | 陌生人不能再锁死管理员，限流表不再无界增长 |
| 重置密码与 PAT | 管理员重置只使会话失效 | 管理员重置同时撤销该用户的全部 PAT（审计详情记 `revoked_pats`）；自助改密码保持 PAT 不变、撤销其他会话 | 重置通常是账号丢失或泄露后的恢复；自助改密码不应打断用户自己的自动化。**这是我替用户做的取舍，可以否决** |
| 邀请的有效性 | 邀请只检查未使用、未过期、未撤销 | 兑换时发出者必须仍是启用的管理员；删除账户时撤销它发出的全部未用邀请和重置链接；停用或降级的发出者的链接兑换时被拒 | 链接带着发出者的权限 |
| 操作中的管理员 | 管理操作只在入口检查身份 | 停用成员、创建与撤销邀请在写事务内复查执行者仍是启用的管理员（401 / 403） | 避免两个管理员同时互相停用而无人可恢复 |
| 脱敏 | 基础正则，只处理白名单后缀 | 增加带引号与 JSON 转义的键、`hf_`、`ghp_`、`github_pat_`、`AKIA`、`AIza`、`xox`、URL 里的 `user:pass@`、裸 `Bearer`；任何能按 UTF-8 解码且不含 NUL 的文件都脱敏（上限 64 MiB）；Hub 调用把凭据值作为已知秘密传入 | 原来的覆盖面太窄，且白名单外的文本文件完全不处理 |
| 评分指标 | `primary_score` 写死取 `reward` | `RunSpec.metric_id` 由受理时冻结的契约给出，`raw_score = rewards[metric_id]`，只有默认指标 `reward` 才允许“唯一的值”回退；成功时也保留全部奖励到 `metrics_json`；缺失或非有限即“无可用奖励” | 管理员确认的指标此前只是标签，实际仍算 `reward` |
| 评分契约取值 | 接受并回显任意聚合字段 | 只接受已实现的 `mean_of_scored_repetitions`、`macro_mean_of_task_means` 和 `count_as_failure: []`，其余在写入时 422；空的 `metric_id`、`name` 也被拒绝 | 回显的契约不能和实际计算不一致 |
| 汇总数值 | 浮点求和与自写标准差 | 均值与标准差用 `statistics`，相同分数的标准差恰为 0；用量的“未知”只统计已开始的试次；标为已评分但没有合法数字的记录归入排除（`unclassified`）而不是丢失 | 浮点噪声与口径不一致 |
| 准备的失败路径 | `check()` 的异常和同时运行任务的取消处理不完整 | Docker 检查的异常按分类后可重试的恢复失败处理；任一任务失败时取消并等待同级任务（`gather_or_cancel`）；清单不被支持的任务单独记为 `PREPARATION_UNSUPPORTED`；环境镜像的“不可得”可经重新导入恢复；被取代的恢复其等待者记为 `cancelled`；撤销准入后的冷缓存运行仍能取得准入输出 | 避免占用标记泄漏、整个运行或整个导入因一个任务而失败、不可得永久卡住 |
| Docker 错误分类 | 通用的“未授权”也算鉴权失败，确定性的构建失败也重试 | 只把拉取与登录的拒绝算鉴权失败；新增不重试的 `FAILED`；只重试已知的暂态原因；构建时限上限 3600 秒（`MAX_BUILD_TIMEOUT`，取值是我定的） | 构建里的 `pip` 401 不应把管理员引向 Hub 凭据。真实测试还发现：BuildKit 在 `RUN` 步骤失败时（`did not complete successfully`）会把命令原文在错误行、指令行和 Dockerfile 摘录里各回显一次且不带步骤前缀，原来的过滤挡不住，所以这类失败一律判为构建失败，只有步骤自己的输出里出现暂态网络错误才重试 |
| 任务材料 | `tree_digest` 整文件读入、无长度分隔；并发安装同一摘要时后到者失败 | 流式读取并加长度分隔（所有材料与准备规格摘要因此改变，发布前可接受）；输掉竞争而目标校验通过算成功；启动恢复时清扫 `.fetch-*`、`.install-*`、`.remove-*`、无任务引用的材料目录和归档 `.tmp`（恢复报告多一个 `leftovers_removed`） | 双击导入不应报内部错误，崩溃遗留要有人清 |
| 产物对账 | 启动时只会把缺失的产物标为不可用 | 同一原因标记的产物在文件回来且大小一致（小文件还核对摘要）时恢复为可用；缺失过半时记错误日志 | 一次挂载失误不应让一周的产物永久不可用 |
| 清除的收尾 | 数据库先提交，之后删文件，遇错即停且无人重试 | 逐个尝试并把 `files_failed` 记入回执；维护循环每 10 分钟清扫无索引行（或行已删除、已过期）且超过 1 小时的文件；准备镜像与材料的清理也逐项尽力 | 文件先写后建行，所以只判定超过宽限期的文件 |
| 导出 | 失败的构建每轮重试、会饿死回收；无数量与磁盘限制 | 构建出错标为失败（`EXPORT_BUILD_FAILED`，不重试，所有者重新申请）；回收与过期先于构建，各自独立；每轮最多构建 4 个；每个用户同时排队或构建最多 2 个（429 `EXPORT_LIMIT_REACHED`）；磁盘低于受理水位时 503 `STORAGE_LOW`；`/capabilities` 的 `limits` 多一个 `export_max_active_per_user` | 一个坏的导出不能停掉回收；一个只读 PAT 不能排上百个 10 GiB 的导出 |
| 导出的操作记录 | `/operations` 对所有人显示导出操作 | 导出操作只有所有者和管理员网页会话可见，其他人 404 | 与导出本身的可见性一致 |
| 下载响应头 | 文件名原样放进 `Content-Disposition` | ASCII 兜底加 RFC 5987 的 `filename*=UTF-8''…`，去掉控制字符、引号和反斜杠，过长截断并保留扩展名 | 中文文件名会 500 |
| 汇总一致性 | 试次产物计数仍含已回收的、导出 `artifact_bytes` 含过期与缺失的文件 | 计数与 `/artifacts` 一致；`artifact_bytes` 为实际打入导出包的字节，含运行级文件 | 同一数字在不同位置应相同 |
| 应用加固 | `/%00` 与超长路径段返回 500；响应没有安全头；`app.db` 为 0644 | 这类路径回到页面；所有响应带 `X-Content-Type-Options: nosniff`、`Referrer-Policy: same-origin`、`Content-Security-Policy: frame-ancestors 'none'`（不加脚本或样式的 CSP，以免影响构建出的页面和 Swagger）；`app.db` 及其 `-wal`、`-shm` 为 0600 | 低风险的加固 |
| 能力声明 | `features.dataset_import` 恒为 `false` | 改为 `true`；`actions` 增加 `catalog.search_source`、`datasets.import`（均仅管理员） | 与已实现的接口一致 |

验证范围：服务测试 393 项通过（修复前 152 项，新增 241 项），连跑两次一致；Docker 与 Hub 的可选测试随后已重跑，见下文“真实测试”；`ruff check` 与 `ruff format --check` 干净。对修复后的代码另做一次变异检查（把一条修复改坏，看测试能否发现），结果见下。修复前，实时日志脱敏和 Docker 清理的实例标签保护这两项改坏后全部测试仍通过。Runner 的符号链接修复另用最初的复现脚本对比：原代码发出了宿主文件内容，修复后什么也不发。

变异检查：实时日志脱敏、Docker 清理的实例标签保护、凭据停用后重新加密、Hub 检索的管理员检查（三个入口各改一次）、邀请发出者检查、评分指标、登录限流按来源分桶、重置撤销 PAT，改坏后现有测试都会失败。Runner 的符号链接保护有三层（跳过链接、`O_NOFOLLOW`、打开后核对真实路径）：同时拆掉三层，或只拆最后一层，测试都会失败；只拆前两层时全部测试仍通过，因为第三层仍然挡住，这是纵深防御，不是漏洞。

**真实测试（Docker 与 Hub，2026-10-23，修复分支的未提交状态）：** 先在修复分支里建 Runner 环境（`runner/` 下 `uv sync --locked`，Harbor 0.24.0），用隔离 HOME 和清空的环境变量运行（Hub 测试只放行代理变量）。跑之前对 Docker 的镜像、容器、网络、卷各留一份快照（55 个镜像、3 个运行中的容器、2 个卷、1295 项构建缓存），跑完逐项对比：四类全部相同，没有留下带实例标签的资源，构建缓存没有增长。原有 5 项 Docker 测试和 2 项 Hub 测试全部通过。随后新增 2 项故意失败的用例并在真实 Docker 29.9.1（buildx 0.38）上运行：一个 Dockerfile 的 `RUN` 步骤打印“pull access denied”后以退出码 3 失败，应判为构建失败；一个任务指定不存在的镜像，应判为凭据问题。第一个用例在修复前失败（被判成 `auth`），暴露了真实 BuildKit 的输出格式，样例测试写不出这种格式；已按“失败的 `RUN` 步骤不是注册表拒绝”修正，并把这段真实输出写成单元测试。修复后 9 项真实测试全部通过，Docker 状态与跑之前逐项相同；单元测试现为 428 项。第二个用例在连不上注册表的主机上会跳过，且只在结果明确是连接错误时才跳，所以对真实答复的误判仍会失败。仍未覆盖：真实 Docker 对其他错误措辞的输出（只验证了这两种）、模型 Agent、网络策略、私有数据集。

**审查发现但没有修，留给后续：**

- `docker pull <标签>` 会移动宿主机上同名的本地标签，回收时只移除 `maestro-prep/...` 标签，拉取的镜像留在磁盘。安全的修法需要先用 `buildx imagetools` 解析出 digest，未能在没有 Docker 和网络的环境验证。
- `RunSink.log` 对每个日志块单独脱敏，被切在两块之间的秘密会漏掉。
- 其他管理操作（凭据、回收站里删除另一个管理员）没有“执行者仍有效”的写事务内复查。
- `CREDENTIAL_UNAVAILABLE`（主密钥无法解密）仍按暂态重试；作者 `task.toml` 里 Agent 或验证器超时的 `inf` 原样保存；导入里解析凭据在 `try` 之外，凭据在请求之后被删时 Operation 报内部错误。
- 被 Runner 跳过的产物在服务端没有给用户可见的提示；开始导出构建时不检查磁盘空间；评分指标只能通过 API 设置，网页还不能；`fake_runner` 假定奖励键为 `reward`。
- 请求体大小限制和 `/api/docs` 从 CDN 加载 Swagger 而无 SRI，属于部署层面；经非本机回环的反向代理访问时，uvicorn 需要配置 `forwarded_allow_ips`，否则所有人共用一个来源地址的限流桶。

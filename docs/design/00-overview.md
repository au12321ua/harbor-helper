上级入口：[文档导航](README.md) · 决策来源：[决策记录与需求追踪](14-decisions.md)

## 1. 目标与使用闭环

Maestro 是面向一个受邀团队的实验平台。管理员接入数据集并通过首次准备建立任务准入，成员通过网页或 Agent SDK 提交实验，系统固定配置、按需恢复缓存、调度执行并保留评分与证据，支持查询、导出及下一轮运行。

首个可用版本完成以下闭环：

1. 管理员在网页中添加 Harbor Hub 的明确数据集版本，至少一个任务首次准备成功并准入。
2. 成员或 experiment PAT 查询可提交目录，解析配置并查看作者基准差异；缓存缺失仅提示运行时恢复。
3. 服务端原子受理运行，产生不可变快照、试次计划和操作记录。
4. Worker 在 Docker 环境中执行，分别记录执行、评分、产物与清理情况。
5. 网页与 SDK 查询结果并下载或批量导出；按原配置重跑或修改后创建新运行。

P1 增加集合、任务对齐比较与分析快照，以及带排空的更新、备份和异机恢复。

### 为什么做

Harbor Hub 已提供 Hosted Harbor 远程作业，通过网页、CLI 和 API 使用，官方当前要求申请开通。本项目的定位是自托管、本地 Docker、团队自有凭据与扩展包，以及以 Agent 为操作者的权限、预检、幂等和接续工作流。自建理由是掌握部署和团队工作流，而非上游缺少网页或 API；更详细的比较见 [15](15-stack-harbor.md)。

## 2. 设计依据与约束

### 2.1 原稿已定

| 约束 | 设计含义 |
| --- | --- |
| 一个实例服务一个团队，管理员和成员两种角色 | 所有业务结果团队可读，写操作按创建者与角色控制 |
| Agent 只参与实验，不管理平台 | PAT 即使由管理员创建，也不获得管理能力 |
| 首期 Linux、单服务实例、本机 Docker | 首期不实现多机调度、GPU 或其他环境后端 |
| 重跑和修改后运行均创建新运行 | 原运行不追加业务试次，不被后续配置覆盖 |
| 总运行时限与无人值守迭代上限必须存在 | 受理时检查额度，执行时执行停止条件 |
| 产物默认保留一周 | 评分摘要、配置、操作记录继续保留，产物到期可回收 |
| 版本准入与准备缓存分开（A9） | 缓存回收不撤销准入；运行自动恢复同一内容，并发共享恢复 |
| 附件安装属于已授权运行（A9 / B2） | 成员 / experiment PAT 可触发；仅本试次容器，无宿主目录挂载，受超时和阶段网络限制 |
| 不迁移旧系统数据 | 从空实例初始化，旧数据仅可作为测试材料 |

### 2.2 本次设计采用的建议

以下为一致性设计的工作基线，决策状态见 D-001 至 D-019；技术路线来自补充建议，具体版本仍待接入验证：

- 服务端采用 Python / FastAPI / Pydantic 模块化单体；Worker 首期在服务进程内，Harbor 在独立 uv 环境中由 Runner 子进程调用。
- SQLite WAL、SQLAlchemy 2、Alembic 保存业务数据与持久队列；asyncio 调度，本地文件系统保存产物，Worker 不直接访问数据库。
- FastAPI 输出公共 OpenAPI；React / TypeScript 网页客户端与 Python httpx SDK 使用同一契约，CLI 建议用 Typer。
- 每个工作单元对应一个计划试次；基础设施重试使用执行尝试记录，不增加计划试次数。
- 错误、重试和奖励有效性以锁定版本 Harbor 策略为基线；结果另记录计分口径、覆盖率和样本量。

网页静态文件由服务端托管，生产不依赖 Node。密码使用 Argon2id，业务凭据采用 AES-GCM；uv 独立发布环境配合 systemd / journald。发布渠道、精确依赖版本与支持的 Linux / Harbor 组合仍待验证，详见 [15 技术栈与 Harbor 集成](15-stack-harbor.md)。

## 3. 范围与优先级

| 模块 | P0 必须包含 | P1 / P2 |
| --- | --- | --- |
| 数据集 | Hub 搜索、不可变版本、任务目录、管理员首次准入、局部可提交、运行内共享恢复 | 本地或私有数据源需另行确认 |
| 配置 | 模型、Harness、附件版本、分层解析、来源、内容快照 | 更复杂的附件组合与兼容策略 |
| 提交 | 方案、单次与批次提交、幂等、PAT 额度、重跑、取消 | 更复杂的实验矩阵生成 |
| 执行 | FIFO、资源准入、进程内 Worker、状态恢复、环境清理 | 公平调度 P1；多机 Worker 后续 |
| 结果 | 单运行查询、任务结果、基本统计、日志、下载和批量导出 | 集合、比较、分析快照 P1 |
| 访问 | 网页、PAT SDK、能力发现、统一操作记录 | JSON CLI 为设计建议；事件流与 webhook P2 |
| 运维 | 安装、启停、状态、日志、保留数据卸载、异常恢复 | 排空更新、备份与恢复 P1 |

首期非目标：多团队、GPU、金额或 token 的强制预算、原运行内续跑、旧数据迁移、RSI 专用隔离、多机 Worker、Docker 之外的环境。费用与 token 可记录观测值，未知时保留为空。

## 4. 规模与容量

| 项目 | 原稿基线 | 设计处理 |
| --- | --- | --- |
| 团队人数 | 15 人，初期活跃 2～3 人 | 无需独立队列集群 |
| 单试次默认资源 | 1 核、2 GB 内存 | 可覆盖，但受团队上限和主机容量限制 |
| 同时执行试次 | 约 10 个 | 槽位、CPU、内存和提供商并发共同约束 |
| 单试次产物 | 通常不超过 100 MB | 作为估算值，不当作已确认硬上限 |
| 产物保留期 | 7 天 | 从试次执行终态计时；具体回收规则见 07 |
| 单运行最大规模 | 原稿待估计 | D-011 给出建议初值，压测后调整 |

10 个默认试次约占 10 核、20 GB 内存，主机还须为系统、数据库、Harbor 网络控制 sidecar 和镜像构建预留资源。一周 1000 个试次按每个 100 MB 估算约需 100 GB，镜像、准备缓存和导出包另计。

性能验收采用与真实 Harbor 隔离的假执行器测量，避免模型调用延迟掩盖平台开销。建议在上述规模下，普通列表与详情请求的 p95 小于 1 秒；具体测试机器、数据量与阈值在实施前记录，属于设计目标。

## 5. 架构与依赖方向

~~~mermaid
flowchart TB
    Web[网页] --> API[统一 API 与身份权限]
    SDK[Agent SDK / 建议 CLI] --> API
    API --> Catalog[数据集与配置目录]
    API --> Runs[方案、提交与运行服务]
    API --> Results[结果、产物与分析服务]
    Runs --> Queue[持久队列与调度]
    Queue --> Worker[进程内 Worker 接口]
    Worker --> Executor[执行器协议适配器]
    Executor --> Runner[独立环境 / Runner 子进程]
    Runner --> Env[Harbor BaseEnvironment]
    Env --> Docker[本机 Docker]
    Catalog --> Source[数据源适配器 / Harbor Hub]
    Worker --> Store[存储接口]
    Runs --> DB[(SQLite WAL)]
    Results --> DB
    Catalog --> DB
    Store --> Files[(本地文件存储)]
    Ops[独立服务管理入口] --> Service[systemd 与发布目录]
~~~

业务层使用自己的 DatasetVersion、TaskAdmission、RunSnapshot、TrialResult 等对象。Hub 响应在数据源适配器转换；Harbor 配置、结果类型与 BaseEnvironment 依赖集中在独立 Runner 内。管理员首次准备与运行内缓存恢复调用同一准备协议，权限入口与成功后的准入处理分开；服务进程不 import harbor。

| 边界 | 输入 / 输出 | 首期实现 | 验证替身 |
| --- | --- | --- | --- |
| DatasetSource | 搜索条件、版本引用 → 内部目录和内容描述 | Harbor Hub | 固定测试目录 |
| ExperimentExecutor | 不可变执行规格 → 进度、评分、产物清单 | Runner JSON 协议 + 锁定 Harbor | 可控制失败点的执行器 |
| RuntimeEnvironment | 环境规格 → 准备记录、环境句柄、清理结果 | Runner 内 BaseEnvironment + Docker / 原生网络策略 | 内存环境 |
| Repository / ArtifactStore | 内部实体、文件流 → 持久记录、存储键 | SQLite + 本地目录 | 临时库、临时文件存储 |

上述方法名是平台接口设计，Harbor 或 Hub 是否提供一一对应的方法需验证，见 D-010。

## 6. 跨模块不变量

1. 配置、试次身份和来源关系受理后固定；执行状态、结果与产物索引可按生命周期更新。
2. 一个计划试次最多有一份被接受的最终结果；旧 Worker 的迟到上报不能覆盖新执行尝试。
3. 验证器给出且 reward_valid 为真的 0 是有效分数；没有评分保持空值，有诊断奖励但无效时不得纳入统计。
4. 接收运行、消耗 PAT 提交额度、写入试次计划和幂等结果必须属于同一事务。
5. 已有运行不因修改方案、目录条目、默认值而被重写；安全撤销和实时容量仍会影响其可执行性。
6. 清理失败不推翻已有评分；产物过期不删除运行、评分和证据过期标记。
7. 网页与 SDK 共享业务服务；PAT 管理能力限制在服务端强制执行。
8. 重启恢复对管理状态的掌握，不自动恢复上一次容器中的执行。
9. 准入、固定内容可得性、本机缓存分别记录；回收与暂态恢复失败不撤销准入，同一固定内容的恢复不得替换为其他 digest。
10. 共享恢复有独立租约与等待关系；单个等待运行取消不终止其他运行所需工作。附件安装在每试次容器独立进行，P0 不共享安装成果。

## 7. 推荐实施顺序

先建立领域类型、权限、操作记录和假适配器，再实现“准备一个假任务 → SDK 提交 → 执行 → 下载”的纵向闭环。随后接入真实 Harbor，完善故障、批次和网页；P0 验收通过后再增加分析与高级运维。具体交付物见 [测试验收与实施计划](13-testing-plan.md)。

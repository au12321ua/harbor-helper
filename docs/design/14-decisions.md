### D-020 本阶段的运行级调度（设计建议，落实 U-05）

- **工作单元暂为运行。** 一个运行由一个 Runner 子进程执行一个 Harbor Job：Job 内 `n_attempts` 取每任务计划试次数，`n_concurrent_trials` 取运行并发。05 第 2～3 节和 15 第 4、6 节中“一个执行尝试对应一个 Harbor 试次”的描述，在本阶段不适用。
- **试次与执行尝试仍是持久记录。** 受理时按任务 × 计划试次数写入 trials；Runner 从 Job 内各试次的目录和结果上报阶段、结果与错因，映射为 execution_attempts。状态、评分、比较和部分重跑都基于这些记录，与将来改为试次粒度后一致。
- **重试。** 本阶段使用 Job 内重试，平台不再叠加外层重试。可否重试由平台错误策略决定（U-15），适配器把它翻译成锁定 Harbor 的 `RetryConfig` 异常名单并显式下发，不依赖 Harbor 默认名单。每次 Harbor 内重试能否识别为独立的 ExecutionAttempt，见 V-12。
- **容量。** 运行按“并发 × 单试次资源”整体预留；提供商并发按各运行的并发之和计算。
- **准备缓存。** 运行启动前确认该运行全部任务的缓存，缺失时加入共享恢复，等待者关联到运行。
- **租约与取消。** 租约和迟到结果防护按运行的 Runner 进程实施；取消粒度为运行，不提供单试次取消。
- **以后的切换。** 改为试次粒度时表结构保持不变，只修改领取规则和 Runner 输入。

### M1 验证记录

**2026-10-22，V-10 / TECH-01 与 V-12。** 范围：Harbor 0.24.0（最新稳定版，U-15），独立 uv 环境，CPython 3.12.3，Docker 29.9.1，Linux 6.8 单机；原型 Runner 与自定义 Agent，2 个本地 ubuntu:22.04 任务 × 2 试次，正常、SIGTERM、SIGKILL、Runner 崩溃各一次。未涉及真实模型、Hub、网络策略、准备缓存与 bootstrap。

- **V-10 / TECH-01：通过，有缺口。** `Job.add_hook` 的试次生命周期钩子能实时、有序地给出环境启动、Agent 开始 / 结束、验证开始、结束和取消，到达延迟不超过 0.1 秒。Runner 在导入 Harbor 前把 fd 1 留给协议、其余输出转到 stderr；在约 100 MB stderr 以及 Python 和子进程都写 stdout 的情况下，协议无污染、无死锁，前提是 Worker 持续读取 stderr。SIGTERM 协作取消后有最终状态，容器由 Harbor 回收；SIGKILL 或崩溃时只有退出码和最后事件，容器和网络会残留。缺口有四项：没有单独的收集事件和 agent setup 开始事件；结构化日志回调只在 Trial 上，不经 Job 暴露；被强杀后的残留只带 compose 标签，需要 Runner 用 `extra_docker_compose` 补平台标签（只能标到服务），或按 trial_name 推出 compose 项目名来清理。
- **补充实验（同日）：上述缺口的处理已验证。** 收集产物用“Agent 结束到验证开始”这段区间表示。安装步骤由我们的 Agent 包装层在 setup 前后自己发事件，实测落在环境启动与 Agent 开始之间。实时日志有两种做法：一是在 Runner 里包装 Harbor 的内部接口挂日志回调，延迟约 2 毫秒，但收不到验证器和 Oracle 的输出，因为它们在容器内把输出重定向到了文件；二是读取 Docker 挂载到宿主的试次日志目录，延迟在 0.5 秒以内，能覆盖 setup、Agent 和验证，并且每次重试的日志都分得开。所以以读文件为主，回调可作补充。清理方面，Runner 的 compose 覆盖文件不只给 main 服务、也给默认网络贴平台标签（纠正上一条“只能标到服务”）；从环境启动后 0.2 秒到 Agent 运行中强杀，按标签都能找到全部残留，其中也包括只建了网络、还没建容器的情况。未覆盖非 public 网络模式下的 sidecar 和额外网络。
- **V-07 / TECH-02：通过，需平台侧加固。** Harbor 的运行级 `extra_allowed_hosts` 只能增加主机且对 public 任务无效，平台只能改写任务副本来收紧；按“作者与平台取更严、白名单取交集”改写后，阶段切换生效：setup 按作者基线可联网，Agent 阶段只通批准主机，验证阶段断网，作者更严的设置被保留，非 TCP 除 DNS 与 ICMP 外被拒，用允许的主机名去连任意 IP 不会被转发。发现两个缺口：setup 阶段建立的连接在后续阶段一直可用（重定向只作用于新连接）；Agent 阶段结束到验证开始、以及验证结束到容器拆除，Harbor 会恢复成 public。Runner 包装 Harbor 的策略切换（私有接口）后两者都关闭：受限之后不再回到 public，并拒绝未经代理重定向的 TCP。内核不支持时 Harbor 会拒绝而不是退回 public，但会让整个 Job 崩溃，且其能力探测在没有 `/proc/config.gz` 时乐观放行，所以需要平台预检。sidecar 也能贴平台标签。每次切换固定多等约 2 秒。未覆盖：云元数据、IPv6、DNS / ICMP 外传、作者基线受限的任务。
- **V-05 / TECH-03：通过，有待定项（C-08）。** 平台可以完全自己掌握准备：不经 Harbor、不运行 Agent，按环境目录内容摘要构建镜像，再通过任务副本的 `docker_image` 交给 Harbor，Harbor 不再构建，环境启动到 Agent 从约 8 秒降到约 0.8 秒。可复现构建设置下确定性 Dockerfile 重建出的镜像 ID 相同，普通构建每次都不同。共享恢复的原型（单个构建、多个等待者各自取消、最后一个离开才停止构建且不发布）行为正确；数据库租约本身留到 M4。镜像被回收后若直接交给 Harbor，错误看起来像鉴权失败，所以平台必须先确认镜像在本机。Docker 的“仓库不存在”和“需要登录”是同一个错误，不能直接判为内容不可得。
- **V-11 / TECH-04：通过，有待定项（C-07）。** Agent 包装层在 setup 中复制附件、在容器内校验摘要、带容器内限时运行 bootstrap 并单独记日志，再交给被包装的 Agent。成功、脚本失败、超时、摘要不符四种情况都限于本试次，失败时不进入 Agent 和验证；每个容器只有自己的安装结果；setup 中能联网安装，Agent 阶段拿不到安装用的下载源。Harbor 的 `exec` 超时不会结束容器内进程，所以限时放在容器内执行。Harbor 只对按名字选择的 Oracle 传入任务目录等参数，用继承方式包装内置 Agent 会丢失这类按名字的特殊处理，正式实现宜改为组合方式。安装错误默认会被 Harbor 重试，需由平台策略通过适配器决定。
- **V-12：每次尝试可以识别。** Job 内重试沿用同一 trial_name，每次尝试的 TrialResult id 不同，且都会完整触发开始到结束的钩子。但是 Harbor 在重试前会删除失败尝试的试次目录，job 结果只保留重试总数，所以 Runner 必须在结束钩子里归档每次尝试；只靠最终结果文件对账会丢掉前几次尝试的证据。

| 事项 | 原设计 | 实际做法 | 理由 |
| --- | --- | --- | --- |
| 评分契约 | 06 第 2 节：每个数据集版本有管理员确认的契约 | 受理时把契约写进运行快照的 `policy.scoring`。数据集版本的 `manifest_json.scoring_contract` 格式正确时用它（来源标 `dataset_version`），否则用平台默认契约（来源标 `platform_default`）：指标 `reward`、越高越好、按“分数 ≥ 1”判通过、任务内先取均值再对任务取宏平均。格式不对的契约整体退回默认，不猜测通过规则 | 管理员确认契约属于 M4 的导入流程，届时写入 `scoring_contract` 即生效；Harbor 验证器对解出的任务写 1，阈值是显式的，不是“大于 0 即通过” |
| 汇总口径 | 06 第 5 节 | 运行列表、运行详情、`GET /runs/{id}/summary` 和导出包里的 `summary.json` 调用同一个函数。终态时“计划 = 已评分 + 按失败计 + 排除 + 未完成”；运行中另有执行中和排队数。“按失败计”的扩展策略未实现，恒为 0。排除原因优先取结果记录的错因，没有执行器结果的试次取平台原因码 | 网页、SDK、导出给出相同计数（06 第 6 节） |

| 产物到期 | 07 第 2 节：试次终态 + 7 天 | 照此实现：试次终结时给其产物写到期时间，迟到的上传沿用同一时间；运行级产物从运行结束起算。M3 原先按写入时间起算，已改 | 不因上传延迟重新计时 |
| 回收与读 pin | 07 第 7 节 | 维护循环每 60 秒回收到期且没有有效 pin 的文件：先标 `deleting`，删文件，再标 `expired`（原因 `RETENTION_EXPIRED`），索引、摘要和评分保留；试次和运行的文件全部回收后产物状态记为 `expired`。只有导出取 pin（最长 1 小时，超时则导出失败并释放）；单个下载在读索引后立即打开文件，回收删除的是目录项，已打开的读取不受影响 | 下载不需要占用 pin，导出才需要跨多个文件的有界保护 |

| 索引与文件对账 | 07 第 4 节 | 服务启动时、执行开始之前对账：索引为可用而文件缺失的标 `unavailable`（`STORAGE_CONTENT_MISSING`）；没有索引的文件和半写入的临时文件删除 | F-09；放在启动时做，避免把正在写入的新文件误判为孤立 |

| 凭据“在用”的判断 | U-19 | 查看排队或执行中运行快照里的 `provenance.credential_ids`。模型配置与凭据绑定属于 M5，届时须把绑定的凭据写进这个字段 | M5 之前没有运行使用凭据 |
| 删除范围 | 07 第 8 节列出的全部对象 | 已实现：运行、产物、数据集、数据集版本、凭据、账户、PAT。方案、批次、附件、模型配置、Harness、集合和分析快照在对应模块实现时接入同一框架 | 这些对象目前没有接口 |
| 删除数据集版本时回收准备缓存 | U-19 | 未实现：只删除任务材料。准备缓存、镜像归档和镜像在 M4 实现，合并时在 `recycle.purge_versions` 中接入（代码中有 TODO） | 准备缓存由并行的 M4 实现 |
| 导出与物理删除竞争 | 07 第 6、8 节 | 物理删除运行或产物时作废已完成的导出包；正在构建的导出在结束时复查，期间有相关内容被物理删除则构建失败（`EXPORT_CONTENT_PURGED`），不发布 | 独立审查发现：构建中的导出原先会在删除之后照常发布 |
| 最后一个管理员 | U-19 | 有检查，但实际由“不能删除自己”保证：执行删除的管理员本身就是另一个有效管理员 | 防御性检查保留 |

**2026-10-23，数据集与准备。** 与 M6 并行开发，按用户指示合并时以 M6 的结果为底、重新生成迁移 `0001`。以下是实现中的选择，均为设计建议层面，未经用户逐条确认；与原设计不同的已写明原写法和理由。

**2026-10-23，对 M2、M3、M4、M6 的独立审查及修复。** 起因：用户只看过汇报、没有读过代码，要求独立评估。审查在 `302b2ff` 上进行，用清空环境重跑测试，并在全新实例上走了真实进程；四个审查者分别查数据集与准备、结果与回收站、身份与 API、执行内核，每条发现都另行重跑复现脚本确认后才修。修复在 `fix/review-findings` 分支上完成，每条带先失败后通过的回归测试。原始复现脚本与报告在 `/tmp` 下，不入库。用户决定见 U-20；以下是实现中的选择，均为设计建议层面。

| 事项 | 原做法 | 新做法 | 理由 |
| --- | --- | --- | --- |
| 实时日志读取 | Runner 的 `tail()` 用 `is_file()` / `open()` 读容器可写的 `agent/`、`verifier/` 目录 | 不跟随符号链接：`O_NOFOLLOW` 打开并核对真实路径仍在试次目录内；归档不再 `copytree`，只复制普通文件，数量（500）、单文件（64 MiB）和新增的每次尝试总量（1 GiB）在复制过程中生效；跳过的文件仍在清单里并带原因（`SYMLINK`、`TOO_LARGE`、`TOO_MANY_FILES`、`TOTAL_LIMIT`、`UNREADABLE`、`COPY_FAILED`），清单最多列 200 条、其余只计数（协议新增可选字段 `skipped_unlisted`） | 容器能写这些目录（C-07），符号链接可让宿主机文件进入全团队可见的日志 |

### 部署上限进入 config.toml

**2026-10-23。** 起因：审查修复新增了几个写死的数字（归档总量、构建时限上限、Hub 并发等），用户指出构建时限、限流、归档上限等应该可以配置。按 U-21 把数值上限分三类，本次只做第一类。以下是实现中的选择，均为设计建议层面。

| 事项 | 原做法 | 新做法 | 理由 |
| --- | --- | --- | --- |
| 配置项 | 数字写死在 Runner、执行器、准备环境、Hub 数据源和导出里 | `Settings` 增加 12 个整数项（键名、默认值与含义见 [12](12-operations.md) 第 3 节），默认值等于原来写死的数字，所以不改变现有行为 | 只有与机器和磁盘有关的才进 `config.toml`；团队策略随 M5 进数据库，结构性常量写死 |
| Runner 的归档上限 | `job.py` 里的模块常量 | 随每个运行的请求下发（`artifact_limits`），Runner 缺少或收到不合法的值就拒绝运行；服务端的脱敏上限取同一个单文件上限，因此收集到的文本文件都被扫描 | Runner 是独立进程，不读服务的配置 |
| 校验 | 只检查路径 | 每项是整数并在范围内（范围表 `TUNING`）；单文件上限不能大于单次尝试总量，默认构建时限不能大于最大构建时限，静默时限至少是心跳间隔的 3 倍；写错、越界或拼错的键拒绝启动并指出哪一项；导出上限高于停止派发水位只在启动时警告，因为小磁盘上调低水位是文档里推荐的做法 | 配置项之间有关联；硬矛盾拒绝，调优上的可疑组合只提醒 |
| 构建时限的生效 | 导入时按固定上限截取并记入准备规格 | 导入记录的仍是当时截取后的值，每次构建再按当前上限截取一次 | 调低上限能立即作用于已导入的版本，又不改变它们的准备规格摘要 |
| 导出上限 | `limits.py` 的 `EXPORT_MAX_BYTES` | 移到 `config.toml`（`export_max_gb`），从 `limits.py` 删除 | 它取决于磁盘，不是团队策略 |
| 生效值的报告 | `/capabilities` 的 `limits` 只有固定常量 | 合并配置生效的值：`export_max_bytes`、`artifact_max_files`、`artifact_file_max_bytes`、`artifact_attempt_max_bytes`、四个时限、`restore_slots`、`hub_runner_slots`（心跳与静默时限属于运维细节，不报告） | 客户端要看到实际生效的值 |
| 默认值的两处 | — | 数字在 `Settings` 和各组件自己的构造默认值里各有一份（测试和直接构造组件时使用），由测试保证一致 | 避免组件反向依赖配置模块 |

没有做：团队策略类（PAT 期限与额度、单次运行的任务数与并发与时限、产物保留天数、导出保留时间、邀请有效期、登录限流次数）仍在 `limits.py`，随 M5；单次尝试的实时日志上限（1 MiB）、清扫与维护的间隔和宽限期、每轮导出构建数等内部节奏参数仍写死。

验证范围：服务测试 424 项通过（此前 393 项），连跑两次一致；`ruff` 干净。新增测试覆盖默认值、范围、关系、类型、拼错的键、导出警告，执行器把配置的上限发给 Runner、Runner 拒绝缺失或不合法的上限、归档按下发的上限生效、命令行把配置接到执行器、准备环境和 Hub 数据源、服务把配置接到准备器和导出、`/capabilities` 返回生效值，以及默认值不漂移；另在真实命令行上确认三种写错的配置各给出一行清楚的报错，以退出码 2 结束，且不创建任何目录。真实 Docker 与 Hub 测试随后已在这些改动上重跑并全部通过，见上一节的“真实测试”。

| 首个 Harness | 03：Harness 由执行器适配器实现 | Harbor 执行器声明一个适配器 `terminus-2`（Harbor 0.24.0 自带），支持三种协议：OpenAI 兼容与 Anthropic 走 LiteLLM，OpenAI Responses 用它的 `use_responses_api`；可暴露的 Harness 参数限定为 8 项（轮数、解析器、上下文摘要、终端录制、窗格大小等），发布 Harness 版本时只许声明这些。服务端与 Runner 各有一份清单，测试保证一致 | U-25；Terminus-2 在 Runner 进程里调模型，容器里只执行命令，可读性最好、安装最轻 |
| 凭据交付 | 15 第 5 节：受保护环境或权限受限文件 | 服务在执行时（不是受理时）解密绑定的凭据，经 stdin 交给 Runner；Runner 只放在内存，由 Terminus-2 的小子类在建模型客户端时传入 `api_key`。不进 Runner 的环境变量（作者的 compose 文件可以引用环境变量，把它带进容器），也不进 Harbor 的 Agent 参数（Harbor 会把它写进试次目录的 `config.json`，成为证据）。凭据在受理后被停用、删除或无法解密时，运行不启动，试次记为执行错误 `CREDENTIAL_UNAVAILABLE` | 03 第 5 节“用当前有效凭据”；09 不让密钥进入容器与证据 |
| 秘密的脱敏 | U-10：基本脱敏 | 本次运行用到的凭据值作为已知秘密，在实时日志、收集的文件、错误信息和 Runner stderr 里额外按值替换 | 基本规则匹配不到自定义格式的 key |
| 作者参数取值 | 第一段只解析不交付 | 参数值（秘密参数在执行时从凭据读出）放进 Runner 的环境变量，由 Harbor 解析 task.toml 的模板；名字已在解析时排除平台保留的 | 这些值本来就是给任务的 |
| 平台网络策略（U-18） | 09、TECH-02：执行 / 验证只访问模型提供商 | 模型运行时每个任务改写私有副本，各阶段取作者与平台中更严的：Agent 阶段——Harness 在容器里调模型时只放行模型地址，Terminus-2 不需要，直接断网；验证阶段一律断网；安装阶段沿用作者基线。Runner 包装 Harbor 的策略切换（私有接口，版本锁定）：一旦受限就不再回到 public，并重置没经过代理的 TCP 连接（M1 发现的两个缺口）。实际计划写入运行证据 `runner/network-plan.json`；sidecar 也贴平台标签。Oracle 测试模式仍按作者设置 | U-18；M1 已验证可行 |
| 能力预检 | V-07：无能力时拒绝 | 有受限阶段时，Runner 建 Job 前用 Harbor 的内核探测检查，不支持即整个运行拒绝（`NETWORK_POLICY_UNSUPPORTED`），不退回 public。Harbor 的探测在没有 `/proc/config.gz` 时偏乐观，这种情况下由 sidecar 实际下发规则时失败、试次出错，同样不会放开网络 | 没有在受理时预检：需要起容器，留到后续 |
| 资源与时限覆盖 | 第一段只解析 | 按运行整体下发 Harbor 的 `override_cpus` / `override_memory_mb` / Agent 与验证的 `override_timeout_sec`。Harbor 的 CPU 只接受整数，所以 CPU 覆盖改为整数，不做四舍五入 | D-020 |
| 模型错误映射 | 06、U-15 | 平台错误策略增加 LiteLLM 的异常名：鉴权、无权限、模型不存在不重试；限流、连接、5xx 可重试；请求参数错误、额度不足不重试；内容策略拒绝算“Agent 拒绝任务”。Terminus-2 自己对每次模型调用最多试 3 次，这是 Agent 内部行为，平台的 Job 内重试仍按策略决定，可能重复的费用记在用量里 | F-06 |
| 用量 | 06 | Runner 从试次结果取输入、缓存、输出 token 与费用，写入试次结果，运行汇总已有“用量”一栏 | V-06 |
| 实时可读（U-07） | 05 EXE-03 | Terminus-2 每轮重写 `agent/trajectory.json`（ATIF）。Runner 跟踪这个文件，把新增的步骤（模型的说明、发出的命令、看到的终端输出）转成可读文本作为实时日志 `agent/trajectory`，与其他日志一样受单次尝试 1 MiB 上限与脱敏约束；完整的轨迹文件和终端最终画面照常归档 | 用户要求 Harness 可读性高 |

验证范围：服务测试 445 项通过（此前 440 项），`ruff` 干净，前端构建通过。新增：执行器按 Agent 模式生成 Runner 请求（适配器、模型、断网的阶段策略、凭据只在 stdin、参数取值、覆盖），秘密在实时日志、文件、错误信息、stderr 里都被替换，模型鉴权错误不重试且带用量；Oracle 不带秘密、不改网络；凭据在执行时读取当前值，受理后被停用则运行不启动且全部试次为 `CREDENTIAL_UNAVAILABLE`；服务端与 Runner 的适配器清单一致。真实 Docker 测试 8 项通过、Docker 状态前后相同，其中新增一项用本地假模型服务跑真实的 Terminus-2：Runner 带着 key 调用模型、容器内写出答案、评分 1.0、Agent 与验证阶段的生效策略都是断网、egress sidecar 确实运行、实时日志里能看到每一步的命令、key 不出现在任何保存的文件里，并且 Oracle 对照能出网、模型运行的两个阶段都出不了网（见下）。另有一项真实模型冒烟（默认跳过，需显式开启）：经用户的中转站调用 `gpt-6-luna`，Terminus-2 一个试次完成同一任务，评分 1.0，用量 1590 输入 / 144 输出 token，记录费用约 0.00023 美元，key 不在任何保存的文件里。环境：Harbor 0.24.0，Docker 29.9.1，Linux 6.8。

网络实测（同日，用户关闭 TUN 模式后容器恢复出网）：同一个任务先用 Oracle 跑（沿用作者的 public）作对照，Agent 阶段和验证阶段都能从 example.com 取得 HTTP 回应；再用 Terminus-2 跑模型运行，两个阶段都取不到。探测必须发出真实请求并看到回应：egress sidecar 是透明代理，会先接受 TCP 握手、再按目标主机决定放行与否，所以“握手成功”在受限阶段也会出现，不能当作出网的证据（第一次实测正是因为只看握手而误报了“Agent 阶段能出网”）。关闭 TUN 之前，这台主机上的容器完全出不了网，当时只验证了计划与 sidecar。Terminus-2 需要容器里有 tmux，没有时在安装阶段用 apt 安装，不能出网的主机上会失败；测试任务因此基于本地构建的 `maestro-test/ubuntu-tmux:22.04`（ubuntu:22.04 + tmux，任务另带一个发 HTTP 请求的探测脚本）。

未覆盖：OpenCode 等在容器里调模型的 Harness（届时 Agent 阶段改为只放行模型地址，需要实测 allowlist）；不能出网的主机上为 Terminus-2 提供 tmux（例如由平台复制静态程序）；受理时的网络能力预检；Anthropic 与 OpenAI Responses 两种协议的真实调用（只有映射，没有实测）；云元数据、IPv6、DNS / ICMP 外传（M1 已列的缺口）；恢复缓存期间仍占着模型提供商的并发名额（M4 记录的问题）；附件（第三段）；方案、批次与重跑（第四段）。

### M5 实施记录（第三阶段：附件与每试次安装）

**2026-10-23。** 实现附件发布、配置解析中的附件和每试次安装（TECH-04、E2E-RUN-04）。以下是实现中的选择，均为设计建议层面，未经用户逐条确认。

| 事项 | 原设计 | 实际做法 | 理由 |
| --- | --- | --- | --- |
| 上传格式 | 03 第 6 节：解包检查后发布 | 请求体就是包本身（tar、tar.gz 或 zip），网页和 SDK 发同样的字节；先落到数据目录下的临时文件再解包。`manifest.json` 放在根目录，或放在唯一的顶层目录里（从文件夹打包时常见） | 不需要表单编码；大包不占内存 |
| 不安全的条目 | 拒绝绝对路径、路径穿越、逃出包目录的符号链接、重复冲突文件 | 更严：只接受普通文件和目录，任何链接与设备文件都拒绝；文件名每段只能用字母、数字和 `._+@-`；先逐项检查再写，边读边计数，超限即停 | 规则简单，不必判断链接指向；Runner 可以不加引号地处理 `sha256sum` 输出 |
| 内容摘要 | 03：content_digest + files_manifest | 摘要覆盖每个文件的路径、SHA-256 和可执行位；同样的文件不论用 tar 还是 zip 打包，摘要相同 | 可执行位影响脚本能否运行，属于内容 |
| 名称与版本 | 03：发布后相同版本同摘要返回已有，不同摘要冲突 | 名称 + 版本在全团队唯一（已清除的不算），同内容重复上传返回原版本（200），内容不同返回 409 `ATTACHMENT_VERSION_EXISTS`。任何成员或 experiment PAT 可发布；所有人可选用已启用的版本；发布者或管理员可停用、删除 | 结果全团队共享，按“名称 版本”引用不应有歧义 |
| manifest 字段 | 03：schema_version、name、version、components、entrypoints、parameter_schema、compatible_harnesses、effects、load_order_requirements | P0 支持 schema_version（1）、name、version、description、effects、compatible_harnesses（适配器名或 `["*"]`）、provides（tools / env，用于查冲突）；components 由包内目录体现，bootstrap 由根目录有无 `bootstrap.sh` 体现。entrypoints、parameter_schema、load_order_requirements 未实现，写了就拒绝，不静默忽略；其他未知字段也拒绝 | 未实现的语义不能假装支持 |
| 影响评分的附件 | 03：改变验证或评分的包要显式声明，形成不同评分契约 | effects 含 verifier 或 scoring 的包在上传时拒绝 | P0 没有“不同评分契约”的实现；附件和验证器在同一容器里，未声明的影响无法从技术上排除，这一点只靠声明 |
| 附件冲突 | 03 第 7 节：同名工具、环境变量或入口默认拒绝 | 同一运行里两个附件同名（含同一附件的两个版本），或 provides 里的工具名、环境变量名重叠，解析时报 `ATTACHMENT_CONFLICT`；附件不支持所选 Harness 报 `ATTACHMENT_INCOMPATIBLE`；Oracle 运行不能带附件 | Oracle 不经过 Harness 包装 |
| 安装位置与身份 | 03 第 7 节、M1：Agent setup 中安装 | Terminus-2 的平台子类在自己的 setup 之前安装：依次把附件复制到本试次容器的 `/opt/maestro/attachments/<序号>-<名称>`（Harbor 的文件传输，不挂载），在容器里逐文件比对 SHA-256 与可执行位，再在该目录下用 `timeout` 运行 `bash bootstrap.sh`，环境变量 `MAESTRO_ATTACHMENT_DIR` 指向它，输出写到 `/logs/agent/attachments/<序号>-<名称>.log`（随实时日志显示，并归档）。建目录、比对用 root；脚本以任务的 Agent 用户运行（任务未指定用户时是容器默认用户），不提权 | M1 TECH-04；Harbor 的 exec 超时只结束本地客户端，限时必须放在容器内 |
| 安装时限 | 03：独立安装超时，并受运行总时限约束 | 团队策略新增 `bootstrap_timeout_sec`（默认 600 秒，上限设置 `bootstrap_timeout_sec_max` 3600），本次可覆盖；只算各安装脚本的运行时间之和，复制与比对另有每包 120 秒余量。Harbor 自己的 Agent setup 时限相应放宽为“Agent 默认 + 安装时限 + 复制余量”，让容器内的限时先生效。没有安装脚本时这个字段为空 | 复制慢不应吃掉脚本的时间；运行总时限仍照常生效 |
| 网络 | 03：安装可按准备策略联网，执行 / 验证切到模型服务限制 | 安装处在 Agent setup 中，沿用作者的环境基线（第二阶段的网络收紧只改 Agent 与验证阶段）；之后 Agent 与验证阶段照常收紧 | 作者基线本身断网时，安装也不能联网，这是作者的选择 |
| 内容核对 | 03：内容固定 | 三处核对：服务在启动 Runner 前按摘要重算存储内容，不符或已清除则整个运行不启动、所有试次失败（`AttachmentContentMissing`，不评分）；Runner 建 Job 前再算一次；复制进容器后逐文件比对 | 绝不安装与发布时不同的内容 |
| 失败归类 | 03：bootstrap 失败归为环境 / 附件准备失败，不能伪装成零分 | 平台错误策略新增 `attachment_failed`（不评分、不重试、reward 无效）：脚本非零退出（`AttachmentInstallFailed`）和超时（`AttachmentInstallTimeout`）归入；容器里的副本不符（`AttachmentTransferFailed`）算沙箱失败，按策略在干净容器重试。执行尝试的错误里带出失败的附件、状态和退出码 | 03 第 7 节 |
| 安装记录 | 03：记录摘要、开始 / 结束、出口码、产物与失败原因 | Runner 把每次尝试的安装记录（附件、摘要、目标目录、用户、状态、退出码、耗时）随结果上报，服务存为该尝试的证据文件 `maestro/attachments.json`（来自 Runner，不是容器可写的文件）；执行步骤里新增“安装附件” | 05 的 GitHub Actions 式步骤 |
| 运行记录 | 03 第 5 节：有序版本列表、每包摘要 | 生效配置里固定附件的有序列表（版本、摘要、影响范围、provides、是否有安装脚本）和安装时限，计入配置摘要，调换顺序即不同配置；另建 `run_attachments` 表，用于“正在使用时不能删除”和按附件筛选运行 | CFG-02 |
| 删除与清除 | U-08 / U-19：两步删除 | 有排队或运行中的运行使用时不能删除（`ATTACHMENT_IN_USE`）；清除时删文件，但若另有未清除的版本持有同样的内容则保留（在写锁下复核，避免与同时发布的相同内容冲突）。已结束运行的快照保留附件信息；对它们重跑时内容已不在，按上一行拒绝，不换成别的内容 | 与数据集清除一致 |
| 大小限制 | 第 5 节建议 256 MiB / 1 GiB、10000 文件 | 照此作为结构常量（上传 256 MiB、解包后 1 GiB、10000 个文件），manifest 最大 64 KiB；单运行附件数为团队策略 `run_max_attachments`（默认 8） | 第 5 节 |

验证范围：服务测试 471 项通过（此前 445 项），`ruff` 干净，前端构建通过、无新增 lint 警告。新增测试覆盖：同一组文件以 tar / tar.gz / zip 打包得到同一摘要、可执行位改变摘要；绝对路径、`..`、带空格的名字、符号链接、硬链接、重复条目、超大、文件过多、非归档一律拒绝且不留下文件；manifest 的严格检查；成员 PAT 发布、重复发布幂等、内容不同冲突、read PAT 不能发布、发布者或管理员才能停用；按顺序解析、字段来源、团队上限、调换顺序改变摘要、Oracle 不能带附件；冲突、不兼容、停用、不存在、数量上限；受理事务内复检到附件被停用时拒绝且不扣额度；删除受运行中拒绝、清除后文件消失且快照保留、同内容另有版本时不删文件；上传大小在声明与流式两种情况下都受限、失败不留临时文件。执行器：附件以存储路径交给 Runner，安装记录成为证据，失败试次为 `attachment_failed` 且带退出码；存储内容被改动时运行不启动。Runner 安装器在宿主上用真实 shell 命令模拟容器：按顺序复制、比对、安装，脚本失败带退出码、超时在限时内结束、副本被篡改时不运行脚本、两个“容器”各自安装。真实 Docker（本地假模型服务，不花钱）：成员 PAT 发布三个附件并各提交两个试次——正常的附件在每个试次自己的容器里安装，安装阶段能从 example.com 取得回应，Agent 与验证阶段不能；每个容器里只有自己的安装标记；容器内来自宿主的挂载只有本试次的 `/logs/agent`、`/logs/verifier`、`/logs/artifacts`、Docker 标准的 `/etc/hostname`、`/etc/hosts`、`/etc/resolv.conf`，以及平台 `init: true` 带来的只读 `/usr/sbin/docker-init`（U-16 的例外之外多出的这一项是 Docker 的 init 程序，不是数据目录）；`/opt` 下没有挂载；两个试次评分 1.0。脚本退出 3 的附件两个试次都是执行错误、`attachment_failed`、退出码 3，日志可见，Agent 没有启动（假模型没有收到请求）；安装限时 5 秒、脚本睡 120 秒的附件两个试次都按超时结束。运行结束后没有带实例标签的容器、网络或镜像残留。真实 Docker 全套 9 项通过、1 项（真实模型）按设计跳过，Docker 状态前后相同。之后这台主机的直连出网时断时续（不经平台、直接 `docker run` 访问 example.com 五次只成功两次），“应当能出网”一侧的对照（Oracle、安装阶段）随之偶发失败，“应当断网”的断言从未失败。探测脚本因此改为：最多试 3 次，并在容器带有代理变量时也经代理试；受限阶段每次都被立即拒绝，所以断网的判断没有放宽，反而多了“经代理也出不去”这一条。同日用户在本机给 Docker 设了代理（守护进程一层用于拉镜像；客户端 `~/.docker/config.json` 一层会给新容器注入代理变量）。实测任务容器里没有任何代理变量：Runner 使用自己的 HOME，读不到部署者的客户端配置。所以这类设置只是本机适配，不影响平台运行；测试新增断言保证宿主的客户端代理不会进入任务容器。改后全套真实 Docker 测试 9 项通过、1 项（真实模型）按设计跳过，Docker 状态前后相同。环境：Harbor 0.24.0，Docker 29.9.1，Linux 6.8。

未覆盖：任务指定非 root Agent 用户时的属主调整（代码有，真实 Docker 未跑）；作者基线断网时的安装；镜像里没有 bash、`timeout`、`sha256sum`、`find` 时的表现（安装会以失败结束，没有专门处理）；安装占用的磁盘没有单独限额；恶意脚本主动尝试访问宿主目录或 Docker socket（只验证了容器里没有这类挂载）；Harbor 原生的 skills / MCP 字段映射；Oracle 以外的其他 Harness；SDK（M7）；比较页面中按附件区分评分契约（P1）。部署主机必须经代理才能出网时，安装阶段怎样使用代理（目前平台不把宿主代理交给任务容器；若要提供，需和各阶段网络策略一起设计，例如只在安装阶段注入、受限阶段的允许列表不含代理），待用户决定。

## 5. 可配置数值建议

除原稿已经明确的值外，下表均为建议初值，所有限制通过 capability 和管理配置返回实际生效值。其中与机器和磁盘有关的项已在 `config.toml`（U-21，见 [12](12-operations.md) 第 3 节），团队策略类已进数据库并带修订（见“M5 实施记录（第一阶段）”）。

| 项目 | 建议初值 | 说明 |
| --- | --- | --- |
| 计划试次同时执行 | 10 | 原稿规模约束，还受 CPU / 内存限制 |
| 单试次默认资源 | 1000 毫核、2 GiB | 原稿“1 核 2 GB”的标准单位解释需确认 |
| 单运行总时限 | 72 小时 | 包含排队、准备和执行，必须有限 |
| 单运行任务数 | 最大 1000 | 原稿待估计项，需 V-09 校准 |
| 每任务计划试次数 | 1，最大 20 | 总数仍受单运行限制 |
| 单运行计划试次总数 | 最大 10000 | 防止数据库一次展开过大 |
| 单批次运行数 / 计划试次总数 | 最大 100 / 10000 | 任一超限拒绝整批 |
| PAT 默认期限 / 总受理数 | 30 天 / 1000 个运行 | 网页可下调，管理员定义允许上限 |
| 解析结果有效期 | 10 分钟 | 不预留容量，受理需复核 |
| 幂等记录有效期 | 至少 7 天 | 到期后重试可能创建新工作 |
| 自动重试 | 最多 2 次，退避约 5 / 20 秒 | 按锁定 Harbor retry，受停止条件限制，不增加计划样本 |
| Worker 心跳 / suspect | 10 / 30 秒 | suspect 不等于允许立即重派 |
| 取消优雅期 / 清理宽限 | 30 / 120 秒 | 超过后强制停止或报告清理失败 |
| SDK 轮询 | 1～5 秒 | 抖动并遵守 Retry-After |
| 分页 | 默认 50，最大 200 | 稳定游标 |
| 原始产物 TTL | 7 天 | 原稿已定，起算规则为设计建议 |
| 导出 / 暂存 TTL | 24 小时 | 活跃任务与有限 pin 除外 |
| 导出读 pin | 最长 1 小时 | 超时中止，不能无限延迟清理 |
| 单文件 / 单试次原始产物硬上限 | 建议 256 MiB / 1 GiB | 原稿 100 MB 是通常量级，不是硬上限；超限保留明确标记 |
| 单导出包 | 建议最大 10 GiB | 预检估算，实际达到后停止并报告 |
| 附件压缩 / 解包大小、文件数 | 256 MiB / 1 GiB、10000 文件 | 拒绝压缩炸弹和异常展开；已按此实现（M5 第三阶段） |
| 附件安装时限 / 单运行附件数 | 每试次 600 秒，上限 3600 秒 / 8 个 | 团队策略，可在管理页调整 |
| 停止受理水位 | 可用低于 20 GiB 或 15% | 按实际磁盘配置，不可照搬小磁盘 |
| 停止派发水位 | 可用低于 10 GiB 或 8% | 给已有执行收尾留空间 |
| 服务日志保留建议 | 14 天 | 由宿主 journald 策略决定，不影响数据库审计 / 操作记录 |

阶段性 deadline、验证超时及数据集硬资源约束由作者契约和团队策略明确，不统一编造一个适用于所有 bench 的单任务时限。

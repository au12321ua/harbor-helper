历史候选 `2e5a71f2e7e47c6b19cca2d2219ae62384502097` 的包与 fixture 验证仅属于其固定范围，不批准生产发布。部署前核对实际 commit/tag、包版本、生产 static 与依赖锁一致，分发时重新核包摘要与完整性；重新构建不能默认产生相同 tarball。生产迁移、备份恢复和真实实验另行核验。

## 正式升级前停写与排空

1. 读取现场 `.local/LOCAL_ENVIRONMENT.md`（存在时）和[Web 维护指南](web-service.md)，实时核部署代码/ref、listener、argv/cwd、PID/birth、守护/自动拉起入口、state 路径与外置 master 引用。旧文档 PID 和备份不能当当前现场。盘点全部 HTTP、scheduler、worker、CLI、直接数据库操作及其他 writer，登记未终态受理/任务、资源归属、队列与清理阻塞。
2. 旧版本可能没有新维护开关；初次升级不能调用尚不存在的 admin maintenance endpoint 来保证停写。使用部署现场既有代理/入口控制，或停止旧 HTTP 等阻断新写，并确认 CLI/其他入口也被阻断。按实时 writer/队列情况决定允许已受理项继续排空或由有权提交者/管理员取消并等待资源释放；若停止 HTTP 会影响现有调度，须先明确该现场排空方式与恢复路径，不能假定后台自动继续。新版本维护暂停也仅拒绝新受理，旧键恢复和已受理执行仍可能写入。
3. 完成全部未终态项/准备/清理处置后，停止并实时确认该 state 全部 writer 及自动拉起来源，确认无仍在执行的进程和未释放资源。仅“暂停”或“队列看似空”不能代替这些证据。需要恢复执行的未终态记录必须先有明确恢复策略，不任意标终态或删除。
4. 保全最新一致 state：SQLite 使用一致 backup 方式，按同一停写时点保全数据库及必需冻结输入/结果/权限模式；不回放旧 WAL/SHM。原 state 外 master 和其权限/引用另行安全保全，不输出秘密，不生成新 master、重 init 或改密码。记录备份时点/摘要/模式与恢复映射，隔离正式秘密于公开报告。历史备份不能覆盖后来业务。

## 迁移、恢复受理与回退

在独立部署代码位置准备固定包/环境，先核兼容迁移路径和新表/字段（自动化 keys、幂等 admission、额度、维护门等）；生产迁移/备份恢复未被最终独立演练，需要明确负责人、窗口和回退点。保留旧代码/环境与最新一致 state+原外 master，避免代码换到新版本但静态/API不同步。按现场操作流程迁移、启动并核授权、队列/资源/就绪后才恢复写入口；不得把本页当自动可执行脚本或部署批准。

回退旧代码可能忽略新权限、幂等和维护门；即使旧版能打开新 state，也不证明安全兼容。先阻断入口并确认全部 writer，保全升级后最新业务 state 与原外 master，再决定兼容修复或有损恢复是否获得授权。不能直接覆盖旧备份丢失新业务；不能删除 keys/admission 来“兼容”而隐式开放访问。回退期间保持停写，直到授权/幂等/维护等边界重新得到保证。

# 数据集、任务与运行环境模型评估

> **历史方案，已被用户否定并取代。** 用户随后明确：Harbor 按 benchmark 作者定义管理环境，helper 仅管理来源、调度、缓存保留与结果记录；不要求执行前构建环境，不替换作者镜像，不要求固定重跑使用相同镜像。本文件的独立准备、产物固定和固定重跑门槛不再是当前方向。以下保留原设计与审查历史，不代表用户接受或当前实施要求。

该方案提出独立准备、产物固定及严格同镜像重跑，已被Harbor原生执行方向取代。以下仅保留设计理由与拟议验收条件，不代表当前产品行为。

建议采用用户提出的数据集优先方向：管理员登记任务来源，任务分别声明所需环境；服务在实验准备中解析、取得或构建这些环境，记录实际使用的不可变镜像身份。环境目录和缓存辅助准备，不再要求先选一个镜像才能登记数据集。

## 为什么需要调整

当前 Web 把运行环境作为数据集验证的前置条件，一个数据集绑定一个 `runtime_id`。该环境最终把一个镜像的固定别名传给指定的任务 Compose 变量。只有任务环境确实引用这些变量时才会使用它；任务仍可按自己的 Dockerfile、预建镜像和 Compose 运行。

因此，这个绑定可以表达原 CAD 模板的镜像覆盖约定，却不能完整描述同一数据集中各任务、执行与评分角色、Compose 附加服务的环境。管理员看到的本地镜像列表也只能证明镜像存在，不能证明它适用于哪个任务。

目前实验记录冻结任务内容及一个额外运行镜像；这不等于已经冻结 Harbor 最终构建或启动的全部任务镜像。调整需要同时改变配置体验和环境记录，不能只隐藏原环境选择框。

## 建议的职责划分

| 对象 | 负责什么 | 用户能看到什么 |
| --- | --- | --- |
| 数据集来源 | 包引用、版本、访问方式及所含任务 | 来源可访问、任务列表、解析出的固定版本 |
| 任务定义 | 任务内容，以及执行/评分环境定义和依赖服务 | 各任务使用 Dockerfile、预建镜像或 Compose，是否缺少必需配置 |
| 环境准备结果 | 根据这次任务快照与明确覆盖配置准备环境 | 构建、取得镜像或复用的进度；每个角色/服务的实际镜像身份和失败原因 |
| 镜像与构建缓存 | 减少重复准备的时间 | 哪些任务的哪次准备产物可复用，何时因输入改变失效 |
| 管理员覆盖配置 | 明确处理需要额外变量或部署依赖的任务 | 适用的任务/角色、修改了什么，不自动套用到整个数据集 |

一份数据集可以包含 Python Dockerfile 任务、预建 CAD 镜像任务，以及有数据库附加服务的 Compose 任务。它们独立准备环境，不要求共享一张镜像。相同环境可以跨任务复用，但任务同属一个数据集或名字相同，不构成兼容证明。

该表中的任务环境详情来自任务定义和准备记录，不从本地镜像名字猜测。Docker 列表保留为管理员查看主机库存的入口，可展示平台和身份；只有已有准备关联或管理员明确覆盖契约时才显示与任务的关系。发现一个镜像不自动登记兼容数据集。

## 网页和实验流程

管理员添加来源、固定版本并验证来源权限；成功后可查看任务列表。来源验证不要求本机已有某个业务镜像，也不声称任务已经能够执行。来源元数据未包含任务环境文件时，列表先显示“环境尚未解析”，取得任务快照后再显示声明方式、必需变量、已知部署依赖及解析问题；依赖尚未取得时显示待准备。可独立解析来源，不以 Docker 不可达否定来源权限。

成员选择来源、任务范围、模型方案与实验参数。受理后固定任务快照、模型与覆盖配置，再逐任务解析环境。使用预建镜像时解析并取得确切产物；使用 Dockerfile 时按冻结构建输入准备镜像；Compose 按实际有效定义处理其各服务，不把附加服务遗漏为一个“主镜像”。必要的执行/评分环境分别记录。

准备成功后记录环境结果并进入执行队列。页面区分下载来源、解析环境、等待构建、构建/取得镜像、环境已准备、执行和评分。首次准备通常更慢；后续兼容产物可以复用。是否提前提供管理员“预热环境”动作可以后续决定，不作为本轮方向成立的前提。

来源不可访问、缺变量、平台不兼容、镜像取得或构建失败时，页面指出相关任务及阶段并提供可理解的原因。不会启动付费推理来检查环境；有失败任务时不把整次实验标为环境已就绪，也不静默丢弃该任务。建议首轮先保持实验准备全成功才发布执行，部分任务执行另作明确选择。

Harbor 当前把构建和容器启动放在同一个环境 `start` 流程，服务现有“输入准备”只下载输入、检查额外镜像。将环境构建前移需要真正分开准备与启动，不能直接调用 `start` 后宣称只准备了镜像。

## 环境身份与重跑

需要区分三个概念：

1. **定义身份**：任务环境文件、构建上下文和有效配置的内容摘要，用来解释这次环境准备来自哪里。
2. **产物身份**：实际准备得到的各服务镜像 ID、可取得时的 registry digest、平台，以及它们与任务和角色的对应关系。
3. **执行条件**：本次有效 Compose 配置、资源/网络约束、冻结输入和代理工具配置，说明这些产物如何使用。

定义摘要相同不保证重新构建得到相同镜像：基础镜像 tag、联网安装依赖等可能改变。registry 多平台索引和本机镜像 ID 也不能混为一项。本轮建议记录准确的已观察身份及未知项，不宣称能冻结外部模型、宿主内核或所有运行时联网行为。

执行必须使用准备结果里的确切镜像身份，启动前核对派生配置和每个服务的固定镜像。准备为执行生成独立的派生配置，不改写原任务快照；其中固定各服务的镜像，关闭隐式构建及可变 tag 拉取，并在容器启动后、代理 setup、agent 运行或推理前核对实际容器 `.Image`。不匹配时停止本次执行并收尾，不能只在报告中补一条差异后继续。Compose 的 entrypoint、command 和 healthcheck 可能已经在启动阶段运行，此检查不承诺早于所有任务代码；若后续要求连启动命令也必须在身份检查后运行，则需另验证 create → inspect → start 的依赖和健康检查语义。本轮建议采用启动前固定与核对、启动后阻止代理继续的边界，不将更强保证写成已具备能力。

这套连接必须覆盖 agent、独立 verifier、各 step 的环境，以及启用时的基础辅助服务。Harbor 的普通 extra Compose 注入不能单独解决它：独立 verifier 会清空额外 Compose，而只添加 image 也可能保留原 build/pull_policy。实施应沿用 Harbor 的有效合并、挂载、健康检查和网络语义，再做受测的固定产物适配；无法准确解析的定义应报告具体限制，不自制一套猜测的 Dockerfile 语义。外部构建 context、远端依赖或宿主路径要显式纳入准备记录，不能无声明读取用户现场文件。

执行期的容器、日志、可写卷和试验输出仍按实验隔离；复用镜像不复用上一实验的运行现场。

**代理安装范围的建议决策**：第一轮保留现有运行时代理 setup 和 bundle bootstrap，不把装过代理、执行过任务的容器直接提交成共享镜像。记录预期/实际代理版本、安装决定与结果、安装脚本和 bundle 摘要，并标明联网安装依赖的未知部分。此时“固定环境重跑”准确指任务输入、基础环境产物及运行配置保持，不承诺代理联网安装后的完整文件系统相同。以后可另增无秘密的预安装产物，并把安装输入计入身份；不要求本轮建立完整依赖制造平台。

固定重跑只复用原任务快照、运行配置和原产物身份。原产物在本机可用时核对后复用；本机丢失但可按原固定 registry digest 取得时，恢复并核对原平台及产物身份后继续。无法取得原产物或核对不符时，固定重跑失败并指出缺失角色/服务，不在该动作内重新构建或取得可变 tag。用户可显式选择“按原规格重新准备”，创建新 run 及新准备记录；即使后来得到相同镜像 ID，这也是新准备产生的记录，保留其来源与变化比较。相同 Dockerfile 不是静默改变原重跑环境的理由；仅在本地保存的产物无法恢复时明确失败，不要求为此建设 registry。

结果比较也应从一个额外镜像改为按任务、角色、服务的环境记录判定。旧实验缺少这类观察数据时保留旧证据和未知边界，不补造完整身份或声称严格可比。

## 复用规则与缓存边界

已经完成的环境准备产物可复用的前提，是相关构建输入、有效覆盖、平台和已解析依赖符合本次准备要求，且产物仍存在并与记录身份一致。镜像名字相似、标签相同或能在 Docker 列表中找到，都不能自动建立任务兼容关系。

Docker/BuildKit 构建层缓存只是构建加速。即使命中层缓存，最终也要记录新准备结果的实际镜像身份。可变基础 tag 应记录本次解析身份及更新策略；联网依赖无法完全固定时明确其边界，不以任务目录摘要掩盖不确定性。

建议新准备先解析显式外部镜像引用的实际身份，再匹配已完成记录；若无法解析，也没有本次请求明确可沿用的固定记录，则显示准备失败，不能猜测 tag 未变。对同一完整已接受构建输入，默认可以复用原产物；管理员显式“重新准备”创建新记录并重新取得/构建依赖。apt/npm 等未锁远端内容不以日期猜兼容，也不以禁用层缓存冒充可重现：复用的是明确旧产物，重新构建则重新记录身份和未锁依赖。只修改评分/指令而构建输入相同时可以复用镜像，但任务快照仍不同。

同一准备输入的并发请求应协调构建，在等待后再次核对产物；任务定义、Compose 覆盖、构建参数或平台改变应重新判定。模型 key、Hub PAT 和成员登录凭据不进入构建参数、环境定义身份或镜像层。若任务确需私有构建认证，应作为单独的部署能力评估，不能直接把团队模型 key 传进 Docker 构建。

构建器使用与执行分离的白名单环境和受控上下文；模型凭据仅在执行授权边界注入其需要的调用，不继承到 Compose 构建。当前 Worker 在 Job.run 前设置模型环境变量，不能继续以“后置脱敏”代替此隔离；秘密一旦进入镜像层或缓存，擦日志不能撤回。新设计不把 registry/build 认证混用为 Hub/模型凭据，也不声称对任意恶意任务提供完整沙箱。

缓存可以保留供后续使用，容器、网络、临时卷和构建工作必须有归属和收尾；可写构建缓存也应按用途协调或隔离，不能作为跨实验共享运行状态的通道。缓存磁盘占用与运行并发容量分开管理，不因为保留镜像就把实验标为清理阻塞。

## 成本、取消与故障

首次构建会增加等待、网络及磁盘开销。准备需要受现有可配置容量和超时管理约束，不能移到准备阶段后绕开资源管理；具体默认由实施验证，不在本评估中发明硬数值。

有效策略需覆盖全部服务及准备构建，不能把当前仅作用于 main 的 CPU/内存 overlay 当成附加服务总量保证。准备工作的归属、共享构建等待者和完成发布要持久记录；重启重试沿用同一已受理快照、已接受有效构建输入及已解析外部身份，不静默重新解析可变 tag 改写该准备；核对已完成产物或处理残留，不因为删了未发布目录就断言资源已释放。

取消准备时停止本次下载/构建等待或自有构建操作，不再发布实验。共享构建仍被其他实验需要时，不能因一个请求取消而终止其他请求。Docker 客户端退出不必然表示后台构建资源已停止；收尾记录需要确认实际状态。只有未确认释放的执行/构建资源限制容量，审计异常另列。

构建或启动异常只应影响相应准备/实验，保留阶段和安全诊断。恢复后依据持久记录确定继续准备、复用完成产物或明确失败，避免把不完整构建标为可复用。

## 兼容与迁移建议

新建数据集默认走任务原生环境，不再要求统一 `runtime_id`。现有绑定保留为旧覆盖配置，并在界面标明其变量约定；不自动推断它适用于数据集的全部任务。需要迁移时展示每个任务的有效变化，管理员明确保存新版本，不改正在排队或已完成实验的快照。

现有 manifest 和原生 CLI 保持可读；新环境记录应标明格式与准备模式，旧数据走旧契约，不在此次 Web 模型调整中暗改所有旧 CLI 默认。新任务原生模式不能因为旧全局默认镜像缺失而拒绝来源登记。

建议迁移时启用新旧准备模式并行解释。缺少新模式字段的旧 submission/manifest 显式按 legacy 解释，不能根据当前 catalog 或默认值推断模式。旧 preparing 沿用已受理配置和旧准备契约，queued 沿用旧 manifest，running 按原拥有者及旧清理/恢复契约处理；完成、取消或明确失败均是允许结局，不保证升级后自动恢复执行或成功。切换前核对旧 worker 的加载版本与归属，在实施升级窗口决定保留旧进程完成还是受控停止后按旧规则处理。旧式重跑继续旧规则并标明“统一配置镜像已固定，任务实际环境身份不完整”；跨新旧比较不据此宣称完整环境相同。用户若选择任务级新模式，作为明确新提交而非修改父实验。具体升级窗口在实施交付时根据真实未终态任务安排，本轮不操作现场。

建议先验证完整任务级准备和身份记录，再把Web入口切到来源优先；如果只是删除绑定但实际启动仍会无记录重建，应视为未完成。

## 可验收行为

- 用于验收的 fixture 数据集包含 Dockerfile、预建镜像、含附加服务的 Compose 三类任务，不配置统一业务镜像即可登记来源；页面能分辨来源可访问与任务环境待准备。这是覆盖异构场景的验收样本，不是每个业务数据集的准入要求。
- 一次实验对所选任务分别准备并记录各角色/服务身份，实际启动镜像与准备记录一致，首次构建后相同输入可复用完成产物。
- 改变任一任务环境文件、有效覆盖或平台，不误复用不匹配产物；只改变无关任务时不无故使另一任务环境失效。
- 预建镜像 tag 改变、本机同名镜像被替换或等待期间镜像被删除，执行和重跑不静默换环境。固定重跑分别验证本机原产物存在、按原固定 digest 恢复、无法恢复三条路径；第三条明确失败且不构建或取得可变 tag。“按原规格重新准备”另受理为新 run，不能修改父实验或冒称固定重跑。
- 独立 verifier、step 和启用的辅助服务使用准备记录的身份；不能只固定 agent 的 main。代理安装和 bundle 改变时，页面及比较记录能区分基础镜像相同与运行 setup 未完全固定。
- 两次并发准备相同输入以及一方取消时，构建协调、其他请求与资源收尾符合持久状态；构建失败或超时不启动模型、不发布假就绪结果。
- 新旧环境记录、现有 CAD 变量覆盖、实验身份/权限、取消、凭据绑定与秘密保护都能区分并迁移；缺少完整身份的旧结果不被伪称完整冻结。

以上是建议的后续原型/实现验收，不是本轮已经执行的测试。兼容性、构建取消及 Harbor 准备/启动适配是主要技术验证点。

## 实现草图与事实依据

现状已静态核对：`service_config.py`的数据集保存/验证/ready要求运行环境；`service_app.py`受理冻结数据集绑定；`runs.py`生成单镜像别名、manifest与Harbor JobConfig；`worker.py`只核对该别名；`reports.py`比较一个image_id。任务下载则已经冻结package/digest/字节快照。

锁定Harbor源码显示：任务有独立environment目录与TaskConfig；Docker环境按Dockerfile/prebuilt/Compose组合启动；`environment_id`是目录内容身份，普通Docker路径仍在start里调用compose build，进程内锁不能代表服务跨Worker构建协调。辅助构建函数包含context/参数/platform哈希与文件锁，但不能由此推断所有任务Compose构建已具备同样保证。

工程进一步核对到：MAIN_IMAGE_NAME 虽计算 hb__ 内容名称，当前本地 build 模板并没有使用该 image 字段；不能按注释认定所有普通任务已采用该缓存 tag。Harbor 删除环境时使用 down --rmi local，可能影响未明确命名的任务镜像保留；实际行为需隔离原型验证。资源 overlay 主要覆盖 main，verifier 清空 extra Compose。上述差异均不通过改文字自动解决。

下一轮最小技术原型应先走通：固定任务快照 → 有效构建图 → 构建/取得镜像 → 逐角色/服务锁定 → Harbor实际消费 → 容器身份核对 → 无模型 Oracle 和清理审计。建议覆盖两种异构 Dockerfile、预建镜像、附加服务及独立 verifier，然后再接新 Web 入口与迁移。原型本轮未执行，不能把本地版本源码读取等同于真实 Docker/Compose 适配通过。
